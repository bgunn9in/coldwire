# Проверка трёх режимов на Ubuntu 22.04 / 1 vCPU / 1 ГБ

[English](../validation-protocols.md) | Русский

Дата проверки: **9 ноября 2026**. Каждый режим установлен на новые диски VM.
Действующие внешние VPS, VPN оператора и маршруты Windows не менялись.

## Стенд

| Параметр | Значение |
|---|---|
| Гипервизор | QEMU / WHPX на Windows, q35, headless |
| ОС каждой VM | Официальный Ubuntu 22.04.5 Minimal Cloud Image amd64 |
| SHA256 образа | `7ccdeb8161d7993be8c10ba8ab234cb329b947ac59f2882a8a4eccc781a2710c` |
| CPU / RAM каждой VM | 1 vCPU / 1024 MiB; гостевая MemTotal 1 008 512 KiB |
| Роли | A: реле, B: выход, C: отдельный клиент; D: новый выход для восстановления |
| Сеть | Частный Ethernet между VM, отдельный NAT для APT/HTTPS/SSH |
| SSH | Только localhost-пробросы; на A root, на B обычный пользователь с парольным sudo |
| Пароли | Случайные, со спецсимволами; нет в исходниках/отчёте |

Использован явный `--allow-private-endpoint`, поскольку тестовые адреса RFC1918.
Публичный production-режим требует назначенных публичных IPv4. Образ:
[Ubuntu Jammy Minimal](https://cloud-images.ubuntu.com/minimal/releases/jammy/release/).
До запуска установщика готовились только сеть VM и SSH. Сам VPN
устанавливался автоматически.

Все VM выходят через один внешний NAT. Совпадение ответа ipify само по себе
не доказывает выбор B: дополнительно проверялись настоящий зашифрованный обмен,
peer/socket на B с источником A, путь клиента через частную сеть, независимость
служб и сохранение идентичностей при переносе B. Тестовые приложения в C
используют netns AWG либо локальный SOCKS Xray; default route Windows не меняется.

## Проверки

Мастер устанавливает выбранные службы с нуля по SSH, сохраняет прямые и
via-entry экспорты, проверяет подключение с действующими ключами и подтверждает A.
Результат дополнительно проверяется с отдельной C:

- AWG: настоящий handshake, HTTPS/DNS через туннель, выбор прямого маршрута
  для исключённого IP и передача 8 MiB зашифрованных данных.
- REALITY: HTTPS через VLESS/Vision, dual-stack имя через IPv4, UDP DNS внутри
  TCP-транспорта, отказ доступа к localhost B, 8 MiB данных.
- Неверный UUID и неверный shortId не дают доступ к Интернету; корректный
  клиент после этих проверок продолжает работать. Обычный TLS-запрос к A
  с SNI цели получает доверенный сертификат и h2.
- При `both` клиентские тесты AWG и REALITY запускаются параллельно. Остановка
  одной службы отдельно проверяется подключением через другую.
- Добавление второго клиента, работа исходного/нового доступов, reboot A/B,
  сохранение ключей/UUID/shortId, backup и restore на новую D с другим IP.
- Повторный backup после restore, независимый systemd-таймер отката A и прямой
  клиентский fallback к восстановленному выходу.

| Проверка | AWG | REALITY | Оба |
|---|:---:|:---:|:---:|
| Автоматическая установка новых A/B по SSH | ✓ | ✓ | ✓ |
| Трафик через A с отдельной C | ✓ | ✓ | ✓, параллельно |
| Второй клиент и сохранение первого | ✓ | ✓ | ✓ |
| Reboot A/B, сохранение идентичностей | ✓ | ✓ | ✓ |
| Backup → новая D с другим IP → re-backup | ✓ | ✓ | ✓ |
| Старые клиенты через A после restore | ✓ | ✓ | ✓ |
| Reboot восстановленной D | — | ✓ | ✓ |
| Независимый таймер отката A, прямой fallback D | ✓ | ✓ | ✓ |
| Работа при остановленном втором протоколе | — | — | ✓ |

AWG add-client не менял PID серверного процесса; Xray add-client перезапускал
только Xray. В `both` остановка AWG возвращает forwarding B в 0; это не мешало
локальному TCP-прокси Xray. Перезапуск восстанавливал работу обоих протоколов.
Секретные данные сравнивались по хешам без вывода содержимого.

После восстановления отдельно проверены AWG **UDP443** и REALITY **TCP443**
на одном выходе: оба передавали зашифрованный трафик параллельно. Для этого
на тестовой D применён исправленный unit AWG с правом привязки низкого порта;
после проверки прежний UDP32497 и его набор capabilities восстановлены.

Дополнительно на новом A оставлен **штатный таймер на 5 минут без подтверждения**.
До срабатывания оба протокола работали через A. Через 301,61 с после возврата
install наблюдались forwarding=0 и удаление собственных правил/юнита;
SSH сохранился, оба прямых fallback к D работали. Для предсказуемого срока
AccuracySec явно ограничен 1 с; наблюдение добавляет до 3 с опроса стенда.

Внешние DNS/IP-check сервисы иногда давали одиночный таймаут. DNS-тест допускает
повтор потерянной UDP-датаграммы; проверка IP REALITY использует два независимых
HTTPS-сервиса, как и проверка в установщике. Постоянная ошибка обоих приводит к отказу.
После reboot перед клиентской проверкой стенд ожидает DNS и синхронизацию часов.

## Ресурсы

Измеряется **RSS процесса**, не вся память ОС. Сэмплирование 100 мс,
нагрузка представляет собой передачу 8 MiB с ограничением скорости на сервере.
Предельная скорость не измерялась.
Нагрузка REALITY включает ожидания отрицательных проверок, поэтому средние CPU
разных режимов напрямую сравнивать нельзя. Go GOMEMLIMIT задаёт мягкую цель GC.

| Режим | Процесс | RSS до трафика, KiB | Наблюдавшийся максимум, KiB |
|---|---|---:|---:|
| AWG | amneziawg-go | 5680 | 8832 |
| REALITY | Xray | 31552 | 35532 |
| Оба | amneziawg-go | 4972 | 8304 |
| Оба | Xray | 32252 | 35748 |

В режиме обоих протоколов наблюдавшиеся пики процессов составили суммарно
около **43 MiB** без учёта памяти ОС, nftables, страничного кеша
и тестового сервера нагрузки. Постоянных Docker/Go SDK/компиляторов на A/B не было. Вход A
обслуживается ядром и oneshot-службой без постоянного процесса прокси.

Для нагрузки `tests/observe_server_vm.py` временно поднимает HTTP-фикстуру
на документационном IP loopback. Xray этой версии по умолчанию блокирует
документационные сети, поэтому **только в защищённом VM-тесте** на время нагрузки
добавляется узкое freedom-исключение для одного IP:порта. После теста исходный
конфиг восстанавливается и Xray перезапускается. В production-генераторе этого
исключения нет. Дополнительный процесс измерения не относится к установленному VPN.

## Найденные и исправленные ошибки

1. Проверка X25519 через Python 3.10 EC_GROUP не работает на штатном OpenSSL
   Ubuntu 22.04. Используется поддерживаемый `openssl s_client -groups X25519`
   с проверкой сертификата, TLS1.3 и h2.
2. При umask 077 новый `/usr/local/libexec` получался закрытым для DynamicUser.
   Новые каталоги бинарников явно создаются 0755; существующий закрытый общий
   каталог отклоняется. Секретные state/exports остаются 0700/0600.
3. systemd 249 не принимает `%d` в ExecStart в этом окружении. Путь к
   LoadCredential задаётся `${CREDENTIALS_DIRECTORY}/config.json`.
4. При запрете IPv6 dual-stack DNS мог приводить к отклонению всего домена.
   Серверный DNS и freedom sockopt согласованы на `UseIPv4`.
5. В режиме `both` AWG-профили должны скачиваться сразу после установки AWG,
   до установки Xray. При последующей ошибке они остаются у оператора.
6. Активация и add-client Xray проверяют готовый listener, а не только успешный
   возврат `systemctl start`. Конфиг откатывается при ошибке добавления клиента.
7. Для явно выбранного низкого UDP-порта AWG необходим CAP_NET_BIND_SERVICE.
   Право добавляется только для портов ниже 1024; высокий порт сохраняет
   прежний набор capabilities. Отказ без этого права воспроизведён в VM.

Ключевые отказы закреплены unit-тестами. Также проверены отказ на
подменённый бинарный пакет даже с новым `.sha256`, сохранение серверного
приватного ключа вне экспортов и запрет подтверждения A при сбое одной из проверок.

## Импорт в приложение

В отдельной C установлен официальный **AmneziaVPN 5.1.0.6 Linux**.
SHA256 установщика:
`f60a4f373332dac8465bd9b8e4f233ee3aa32131fe124d31ca70bc499c73496f`.
Приложение запущено на виртуальном X11-дисплее с отдельными настройками для
каждого теста. Штатный `--import` сохранил в serversList:

- AWG `.vpn`: контейнер `amnezia-awg2`;
- Xray JSON: контейнер `amnezia-xray`;
- VLESS URI: контейнер `amnezia-xray`.

VPN из GUI не включался. Передачу данных проверяли нативные движки с отдельной
VM. Импорт в GUI проверял формат файлов; совместимость всех версий
клиента и ОС не проверялась. Физические Windows/macOS/Android/iOS не переключались.

## Воспроизведение и границы

Для независимого сетевого теста подготовьте изолированные A/B/C с частными IP,
установите нужный режим через deploy, скопируйте выданные тестовые профили в C.
`tests/smoke_clients_vm.py --help` описывает параметры: --vm-test, --protocol,
--entry, --profiles, --bin, --reference-file и --report. `--bin` содержит
проверенные клиентские бинарники, а reference-file содержит ответ HTTPS ipify с B.
В C нужны iproute2/nftables/TUN для AWG. Для нагрузки отдельно запустите
observer на B, дождитесь `/root/kit-observer.ready`, после клиента завершите
observer через SIGTERM, чтобы он сохранил метрики и убрал фикстуру.
`--quick` не требует observer и пропускает нагрузку/отрицательные проверки.

Оба тестовых скрипта требуют root и частный RFC1918 endpoint. На действующих
серверах их не запускайте. Полный запуск требует подготовки виртуальной сети;
эти скрипты не являются production-командой диагностики.

На Windows прошли **44/44 unit-теста**, компиляция Python и синтаксическая
проверка PowerShell. Bash-скрипты проверены в Ubuntu. Windows `setup.ps1 --help`
и `setup.sh --help` в новой Ubuntu venv реально установили зависимости и
передали параметры мастеру. Офлайн-генерация воспроизвела оба JSON с хешами
из [lists.md](lists.md); проверены локальные ссылки и вложенные архивы
на реальные доступы, адреса рабочих узлов и локальные пути пользователя.

Проверка не доказывает многосуточную устойчивость, скорость слабого VPS при
любом числе клиентов, доступность target во всех сетях, отсутствие блокировки
DPI или устойчивость к корреляции. IPv6-выход, все сочетания DoH/KillSwitch и
firewall всех хостеров не проверялись. Этот отчёт относится к Ubuntu 22.04
amd64. Ubuntu 24.04 и 26.04 описаны в [более поздней проверке LTS](validation-lts.md).
