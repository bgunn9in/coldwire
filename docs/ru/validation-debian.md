# Проверка Debian 12 и 13

[English](../validation-debian.md) | Русский

Дата проверки: **10 ноября 2026**. AWG, REALITY и оба протокола установлены
с нуля на Debian 12 и 13. Для каждого из шести случаев использованы новые
диски A/B/C: A служил реле, B выходом, C отдельным клиентом. D был новым
выходом для восстановления. У каждой VM были **1 vCPU и 1024 МиБ RAM**.
Действующие внешние серверы, VPN оператора и маршруты Windows не менялись.

## Изменения платформ

Общая проверка ОС в Python и обе проверки в Bash теперь допускают Debian
12/13 вместе с Ubuntu 22.04/24.04/26.04 LTS. Другие версии, производные ОС
только с `ID_LIKE`, архитектуры кроме amd64 и системы без systemd не
поддерживаются. Проверки существующей установки, firewall, SSH-ключей
и бинарных пакетов сохранены.

Бинарники AWG и Xray, службы systemd и параметры протоколов не менялись.
Debian использует готовые пакеты из репозитория. Для пересборки AWG
по-прежнему нужна отдельная Ubuntu 22.04 amd64 с базовой glibc 2.35.

В [примечаниях к выпуску Debian 13](https://www.debian.org/releases/trixie/release-notes/whats-new.html)
описаны обновления Python до 3.13 и OpenSSL до 3.5. Проверены эти версии,
а также Python 3.11 и OpenSSL 3.0 из Debian 12.

| Debian | Ядро | Python | systemd | OpenSSL | glibc |
|---|---|---|---|---|---|
| 12 | 6.1.0-54-cloud-amd64 | 3.11.2 | 252 | 3.0.22 | 2.36 |
| 13 | 6.12.115+deb13.1-cloud-amd64 | 3.13.5 | 257 | 3.5.7 | 2.41 |

## Образы и стенд

Официальные образы genericcloud amd64 получены из каталогов
[Bookworm](https://cloud.debian.org/images/cloud/bookworm/latest/)
и [Trixie](https://cloud.debian.org/images/cloud/trixie/latest/).
Их SHA512 совпали с SHA512SUMS, загруженными по HTTPS. Подписи GPG
отдельно не проверялись. Позднее ссылки могут указывать на новые образы.

| Образ | SHA256 загруженного файла |
|---|---|
| debian-12-genericcloud-amd64.qcow2 | 24036a8b79cbb11d809752c60f2f885b1a3b02b1d663faa0b648eb87bd7a256e |
| debian-13-genericcloud-amd64.qcow2 | de9d63f5e5ec5927d7548bc05b6043b87457b8c1cb9bcb95365168e8d0293b4f |

QEMU/WHPX работал напрямую в Windows. Использована локально исправленная
сборка QEMU 11.1.3 из [исследования перезагрузки](validation-lts.md#обычные-перезагрузки).
WSL2 не использовался. Между гостями была закрытая Ethernet-сеть, отдельно
работал NAT для пакетов, интернета и SSH через localhost. На A использовался
root с паролем, на B обычный пользователь с парольным sudo.
На A/B не устанавливались Docker, containerd, Go SDK или компилятор.

Совместный режим на Debian 13 использовал `qemu64` без AVX/AVX2, остальные
случаи использовали `max`. SSH и закрытая сеть стенда готовились отдельно
от VPN. Мастер установил VPN по SSH, получив адреса, порты, логины и пароли.

Для выбранных протоколов также проверены:

- Передача 8 МиБ зашифрованных данных с отдельного клиента и ожидаемый
  адрес выхода B. Для AWG проверен прямой маршрут исключённого адреса.
- Отказ REALITY при неверных UUID и shortId, запрет доступа к локальному
  SSH-порту B, действующий сертификат цели и h2 при обычном TLS-запросе.
- Работа нового и прежнего клиентов. AWG сохранял PID серверного процесса;
  добавление клиента Xray перезапускало только Xray.
- Одновременные тесты трафика в режиме обоих протоколов. Каждый работал
  при остановленной службе другого протокола.
- Сохранение учётных данных после перезагрузки, резервного копирования
  и восстановления на D с другим частным IP. После обновления назначения
  A оба прежних клиента работали. D перезагрузился и создал новую копию.
- Откат по независимому трёхсекундному тестовому таймеру. SSH сохранился,
  пересылка вернулась к прежнему значению, прямое подключение к D работало.

Итоговая матрица обычных перезагрузок выполняла четыре команды на случай:
A отдельно, B отдельно, затем A/B друг за другом. Все **24** прошли со сменой Linux
boot ID, событиями QMP RESET от гостя, прежними PID и временем создания
процессов QEMU в Windows. Соединение QMP оставалось открытым. После каждого
этапа проверялись автозапуск служб, собственные правила, учётные данные
и трафик клиента. Холодный старт и ручной перезапуск служб не использовались.

Все гости использовали общий внешний NAT хоста. Одного совпадения внешнего
IP недостаточно для подтверждения маршрута: дополнительно проверялись
выбранный вход, обмен с действующими ключами, адрес A на B и правила реле.

Настоящий пятиминутный таймер запускался и подтверждался при каждой
установке. Полное ожидание срабатывания отдельно проверено с обоими
протоколами на каждой версии Debian:

| Debian | Секунд после возврата установщика | Правила удалены, SSH и прямые подключения работают |
|---|---:|---|
| 12 | 303.15 | PASS |
| 13 | 302.51 | PASS |

Точность таймера задана в 1 секунду; опрос каждые 3 секунды добавляет
задержку наблюдения.

## Автоматические проверки и воспроизведение

Все **48/48 модульных тестов** прошли без пропусков на Windows,
Debian 12/Python 3.11 и Debian 13/Python 3.13. На обеих версиях Debian
`setup.sh` создал новую venv, установил закреплённую Paramiko и передал
параметры мастеру. Проверен синтаксис Bash.

Проверка Windows выявила ошибку выбора Python: `py -3` предпочёл
экспериментальную сборку `3.13t`. Это поведение описано в
[руководстве Python для Windows](https://docs.python.org/3/using/windows.html).
Теперь скрипт явно выбирает обычную зарегистрированную версию.
Если прежняя venv несовместима, скрипт останавливается до pip. В новой venv
на обычном CPython 3.13.5 установлена Paramiko 5.1.0; все 48 тестов прошли.

Обе настоящие проверки ОС в Bash дополнительно запускались с пятью
поддерживаемыми и восемью неподдерживаемыми или неполными описаниями ОС
в отдельных пространствах монтирования. Прошли **26 проверок**.
Использовался режим проверки без установки; установка сервера
с подменённой ОС не выполнялась.

Для модульных тестов на компьютере с Debian откройте корень исходников.
Обычный CPython 3.10+ с venv/pip должен быть установлен заранее:

```bash
bash setup.sh --help
.venv/bin/python -m unittest discover -s tests -v
```

Сетевые сценарии находятся в [smoke_clients_vm.py](../../tests/smoke_clients_vm.py)
и [observe_server_vm.py](../../tests/observe_server_vm.py). Подготовьте
изолированные A/B/C с частными адресами, установите VPN мастером с явным флагом стенда и перенесите
выданные профили и проверенные клиентские бинарники на C.
Параметры наблюдателя и клиента описаны в
[отчёте протоколов](validation-protocols.md#воспроизведение-и-границы).
Эти привилегированные сценарии предназначены для одноразовых VM
и отказываются работать с публичными адресами.

## Исправления стенда и ограничения

Для HTTP-данных стенда использовались `nocloud-net` на Debian 12
и `nocloud` на Debian 13 в соответствии с версиями cloud-init. Первая
проверка перезагрузки также успевала получить ответ SSH до перезапуска Linux.
Теперь ожидание требует смены boot ID и повторяет
короткие таймауты SSH/IPv4-DNS в пределах общего срока. Неудачные проверки
перезагрузки после этого успешно повторены.

Один HTTPS-запрос к example.com завершился таймаутом после восстановления.
Прямой запрос с D и последующие клиентские проверки прошли без изменения
конфигурации VPN. Доступность внешних сайтов остаётся зависимостью теста.
Менять службы VPN или параметры протоколов из-за этих сбоев не потребовалось.

В каждом случае A/B/C/D использовали одну основную версию Debian.
Смешанные пары дистрибутивов, обновление уже установленной ОС, физические
клиентские приложения, firewall всех хостеров, все сочетания
DNS/DoH/KillSwitch, многосуточный трафик и обход DPI не проверялись.
IPv6-выход не реализован. Полные VM-циклы Ubuntu для этой правки списка ОС
не повторялись; прежние результаты есть в [отчёте Ubuntu LTS](validation-lts.md).
