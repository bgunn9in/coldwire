# Фильтр AWG Header Protection + MAC1

[English](README.md) | Русский

Это лабораторный прототип для входного реле COLDWIRE. Он проверяет заголовки
AWG перед пересылкой пакетов на выходной сервер. Клиенты AWG 3.1 сохраняют
свои профили; дополнительные приложения не нужны. Обычные установщики
прототип не включают.

Используются один процесс на C, OpenSSL 3 и очередь nftables NFQUEUE.
Входной узел получает HeaderProtectionKey и публичный ключ выхода. Приватный
VPN-ключ выхода, приватные ключи клиентов, PSK и сессионные ключи ему не
передаются. Пользовательский трафик остаётся зашифрованным между клиентом
и выходным сервером.

## Что проверяется

Для входящих пакетов IPv4/UDP, выбранных правилами из примера, процесс:

1. Проверяет длины IP/UDP и использует 12-байтный префикс AWG как nonce ChaCha20.
2. Раскрывает тип сообщения с помощью HeaderProtectionKey.
3. Для начала рукопожатия и ответа расшифровывает защищённые служебные поля
   до MAC1 и проверяет его через keyed BLAKE2s-128. MAC2 и случайный трейлер
   в эту проверку не входят.
4. Пропускает распознанные сообщения данных и cookie достаточной длины.
   Их подлинность проверяет выходной сервер. Фильтр не отвечает на отброшенные
   пакеты и не меняет содержимое пропущенных.

Поддерживаются только **S1-S4=12 и H1-H4=1,2,3,4**: текущие значения COLDWIRE
по умолчанию. Внешний IPv6 и другие сочетания параметров в прототип не входят.
Процесс копирует из NFQUEUE до 212 байт пакета. Этого хватает для чтения
MAC1 инициации с максимальным заголовком IPv4. Длина копии сверяется
с исходной длиной из `NFQA_CAP_LEN` и заголовками IP/UDP.
Парсер учитывает опции IPv4; дефрагментацию выполняет Linux до очереди
с приоритетом raw. Нормализация GSO в NFQUEUE сохранена, чтобы процесс
проверял отдельные датаграммы.

Это не аутентификация клиента. MAC1 использует публичный ключ получателя,
а Header Protection является потоковым шифрованием без проверки подлинности.
Перехваченное рукопожатие можно повторно пропустить через фильтр. Наблюдатель
также может скопировать префикс и заголовок пакета данных, изменив его полезную
нагрузку. Владелец общего HeaderProtectionKey может создавать распознаваемые
пакеты без зарегистрированного клиентского ключа. Некорректный VPN-трафик
по-прежнему отвергает B.

Пакеты I1/Jc не подтверждают подлинность и отбрасываются этим строгим
прототипом. Они остаются на участке клиент→A, но исчезают на участке A→B.
Работающее VPN-подключение не доказывает сохранение прежней маскировки
на обоих участках.

Реализация следует закреплённым в проекте исходникам AWG:
[защита заголовка и рукопожатие](https://github.com/amnezia-vpn/amneziawg-go/blob/1b86b2ae0e493e7ea93f8c1a0f0cb6735b1551f1/device/noise-protocol.go),
[MAC1](https://github.com/amnezia-vpn/amneziawg-go/blob/1b86b2ae0e493e7ea93f8c1a0f0cb6735b1551f1/device/cookie.go)
и [приём пакетов](https://github.com/amnezia-vpn/amneziawg-go/blob/1b86b2ae0e493e7ea93f8c1a0f0cb6735b1551f1/device/receive.go).

## Сборка и автономные тесты

Используйте одноразовую Linux VM. Пакеты сборки нужны только для компиляции:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends gcc make pkg-config libc6-dev libssl-dev libnetfilter-queue-dev
cd experimental/awg-prefilter
make check
```

Тестам достаточно стандартной библиотеки Python. Синтетические открытые
векторы в `test-vectors.json` получены независимо через ChaCha20 из Python
cryptography и BLAKE2s из hashlib. Рабочих учётных данных в них нет.
Проверяются повреждённые пакеты и рукопожатия, неверные ключи, повторы,
подмена полезной нагрузки данных, права файла ключей и ограничения экспорта.

Для AddressSanitizer и UndefinedBehaviorSanitizer:

```bash
cc -O1 -g -std=c11 -Wall -Wextra -Werror -fsanitize=address,undefined \
  -fno-omit-frame-pointer prefilter.c -o prefilter-asan \
  $(pkg-config --cflags --libs libnetfilter_queue openssl)
ASAN_OPTIONS=detect_leaks=1 PREFILTER_BINARY="$PWD/prefilter-asan" python3 test_prefilter.py
```

Для отдельной профилирующей сборки добавьте в команду компилятора
`-DPREFILTER_PROFILE`. В её отчётах есть процессорное время потока
в наносекундах для приёма netlink, разбора пакетов, раскрытия заголовков,
проверки MAC1 и отправки вердиктов. Раскрытие заголовков и MAC1 входят
в общее время разбора. Приём включает системный вызов и извлечение
сообщений из сокета. Замеры времени добавляют накладные расходы,
поэтому скорость сравнивается на обычной сборке.

## Группировка сообщений вердиктов

Отдельная сборка объединяет до 16 индивидуальных сообщений вердиктов
в одну датаграмму netlink. Каждое сообщение содержит точный ID уже
проверенного пакета. Разные решения, пропуски и переполнение ID сохраняют
свои вердикты. Штатный API очереди для группового вердикта распространяет
одно решение на все ожидающие ID до границы, поэтому в этой сборке
используются обычные сообщения `NFQNL_MSG_VERDICT`.
[API NFQUEUE](https://www.netfilter.org/projects/libnetfilter_queue/doxygen/html/group__Queue.html).

```bash
make check-batch
```

Команда собирает `prefilter-batch` и запускает проверки протокола,
закодированных вердиктов и ошибок отправки. Этот бинарник принимает
те же аргументы `--vm-test --queue NUMBER KEYFILE`, что и обычная сборка.
В стандартной сборке `prefilter` сохраняется поштучная отправка.

Для приёма используется `recvmmsg(MSG_WAITFORONE)`: после первой датаграммы
вызов забирает ещё до 15 доступных датаграмм без ожидания. Полная группа
или оставшийся хвост отправляются до следующего блокирующего приёма.
Память приёма ограничена 16 × 8192 байтами. Усечённая датаграмма netlink
или ошибка отправки вердикта закрывают очередь, после чего действует
прежнее поведение fail-closed. Нормализация GSO в ядре и копирование
до 212 байт сохранены.

`receive_calls` и `received_datagrams` учитывают операции приёма.
`send_calls` считает попытки отправки, включая повтор после прерывания,
а `submitted_verdicts` — отдельные вердикты, успешно переданные сокету.
Пересылка пакетов ядром и потери очереди проверяются отдельными счётчиками.

## Проверка на одноразовом реле

Подготовьте изолированные клиент C, вход A и нативный выход AWG B.
Используйте адреса RFC1918, по 1 vCPU и 1024 МиБ на VM. Сначала проверьте
обычный DNAT. Следующие команды предназначены для стенда, а не работающего VPN.

На B экспортируйте два входных параметра фильтра в закрытый каталог:

```bash
sudo install -d -m 700 /root/prefilter-private
sudo python3 experimental/awg-prefilter/export_keys.py --vm-test \
  --state /etc/awg-relay-kit-exit/server.json \
  --output /root/prefilter-private/keys
```

Экспорт запрещён для публичных адресов выхода, неподдерживаемых S/H
и существующего выходного файла. Передайте файл на A защищённым способом,
сохранив владельца root и права 0600. HeaderProtectionKey секретен;
храните файл и захваты пакетов вне Git. Фильтр отвергает символьные ссылки
и файлы ключей, доступные другим пользователям.

На A запустите отдельно собранный бинарник:

```bash
sudo ./prefilter --vm-test --queue 100 /root/prefilter-private/keys
```

После привязки очереди он выводит `ready` и предел копирования. SIGUSR1 выводит накопленные
счётчики JSON; SIGTERM выводит итоговые счётчики и закрывает очередь.
Записи на каждый пакет нет. `bytes` считает исходные байты пакетов,
`copied_bytes` — байты, переданные процессу, `netlink_enobufs` — уведомления
о переполнении приёма. Потери очереди ядра учитываются отдельно.
Длина очереди ограничена 2048; fail-open выключен.
Процесс root задаёт через SO_RCVBUFFORCE приёмный лимит 4 МиБ. Linux
показывает 8 МиБ с учётом своего способа подсчёта. Это лимит сокета,
а не резидентная память процесса; память очереди и сокета дополняет RSS.

Перед применением правил поставьте независимый таймер отката, удаляющий
**только** экспериментальную таблицу. Задайте интерфейс, адреса и порты
стенда в копии [lab-rules.nft.example](lab-rules.nft.example), проверьте её
и загрузите. Существующие правила DNAT/SNAT должны сохраниться.

Правила учитывают совпадение внешнего порта клиента с входным портом A.
Пакеты в ответном направлении conntrack обходят входную проверку MAC1: их получатель
является клиентом. Пакеты с адресом и портом B в исходном направлении
проходят проверку после conntrack, до DNAT. Безусловного доверия адресу B нет.

При сохранённых правилах остановленный процесс или переполненная очередь
приводят к потере пакетов. Для возврата к обычному DNAT удалите таблицу
эксперимента **до** остановки процесса:

```bash
sudo nft delete table ip awg_prefilter_lab
```

Для этого сравнения не используйте откат всего реле COLDWIRE. У прототипа нет
боевого установщика, постоянной службы и интеграции с ротацией ключей.
Истощение ресурсов и заполнение внешнего канала VPS требуют отдельной защиты.

## Ограничение нагрузки в ядре

Необязательный [пример правил ядра](lab-kernel-guard.nft.example) работает
до очереди. Его можно проверить и с обычным DNAT. Каждое сочетание IP
источника и UDP-порта получает лимит 35 000 пакетов/с с запасом 3500 пакетов.
Затем применяется общий лимит 50 000 пакетов/с с запасом 5000 пакетов.
Это настройки стенда. Для другой среды сначала измерьте обычный трафик,
включая одновременную работу нескольких клиентов.

Считайте также потери пакетов клиентов до NFQUEUE. В
[проверке запаса пакетов](validation-v4.ru.md) уменьшение лимитов убрало
переполнение очереди, но часть клиентских пакетов стала отбрасываться раньше.
Нулевые потери очереди сами по себе не подтверждают сохранение полезного трафика.

Динамический набор хранит до 4096 сочетаний и удаляет запись после пяти
секунд простоя. Переполненный набор отбрасывает пакеты новых сочетаний
до освобождения записей. Смена IP или порта создаёт новый счётчик.
Клиенты с общим внешним IP получают отдельные счётчики, если их внешние
UDP-порты различаются. Атакующий может заполнить набор или израсходовать
общий лимит, затронув обычных клиентов.

Для сравнения загрузите только таблицу ограничений с DNAT, затем обе
таблицы с фильтром. Предварительно проверьте каждый файл через `nft -c -f`.
В обоих примерах должны совпадать интерфейс и адреса стенда. Поставьте
таймер отката, удаляющий обе экспериментальные таблицы. Возврат к DNAT
выполняется удалением таблиц.

```bash
sudo nft delete table ip awg_prefilter_lab
sudo nft delete table ip awg_kernel_guard_lab
```

Удалите присутствующие таблицы до остановки процесса очереди.
Основная таблица реле продолжает выполнять DNAT/SNAT.

## Проверка клиента и маскировка

Прототип продолжает проверять каждый выбранный пакет. Для будущего кэша
потребуется подтверждение от B, защищённое от подделки и привязанное
к конкретному потоку с коротким сроком действия. Пакет, похожий на ответ,
или состояние conntrack могут появиться и у неподтверждённого трафика.
Повторно выданный IP должен проходить новую проверку. Допуск одного клиента
не должен открывать доступ всем пользователям за его NAT.

В прототипе сохраняется строгая политика I1/Jc. Их отбрасывание меняет
рисунок пакетов на участке A→B. Для сохранения этого рисунка потребуется
отдельный ограниченный пропуск маскировочных пакетов и измерения обоих участков.

## Измерения

[Проверка нативного коммутатора](validation-v9.ru.md) и её [JSON](results-v9.json)
подтвердили 25 000 входящих шумовых пакетов/с. Все шесть основных прогонов
с фильтром сохранили 100 Мбит/с и CPU ниже 75% у всех четырёх гостей.
DNAT насытил вход. Для [коммутатора стенда на Windows](lab-switch/README.ru.md)
добавлены исходник, инструкция сборки и тесты; установщики VPS его не развёртывают.
[Проверка постоянного сбора](validation-v8.ru.md) и её [JSON](results-v8.json)
воспроизвели пики CPU источника при новых SSH/sudo-запусках сборщика.
Постоянный запуск удержал все четыре VM ниже 75% в шести контролях
с фильтром при подтверждённых 15 000 пакетов/с шума и 100 Мбит/с.
Python-коммутатор стенда ограничил прогоны с запросом 25 000 пакетов/с;
они сохранены как диагностика, без оценки предела мощности фильтра.
[Проверка коротких окон CPU](validation-v7.ru.md) и её [JSON](results-v7.json)
учитывают все четыре VM. При 100 Мбит/с и шуме 10 000 пакетов/с измеренные
окна остались ниже 75% CPU. При 25 000 пакетов/с DNAT насытил вход;
фильтр сохранил скорость в этом сравнении, но пики VM-генератора нарушили
критерий для всего стенда. В стеках ядра есть повторная передача после
вердикта и отправка через Virtio. Прежний большой рост CPU с IFB не
повторился; причина различий группировки между этапами не установлена.
[Профилирование CPU](validation-v6.ru.md) и его [JSON](results-v6.json)
сравнивают обычные и профилирующие сборки. IFB уменьшал группы вердиктов,
профилирование снова меняло их. Средний CPU входа/выхода/клиента в записанных
окнах ниже принятого порога 75% всей VM; пики и CPU источника шума не измерены.
[Проверка очереди сглаживания](validation-v5.ru.md) и её [JSON](results-v5.json)
добавляют снятие счётчиков после остановки трафика, захват поступления
пакетов и контроль `TCP_NODELAY` на коммутаторе. IFB/TBF не принят:
проверенные очереди повышали CPU или теряли пакеты клиентов, а выбор
по UDP-порту пропускал фрагментированный трафик.
[Проверка темпа и запаса пакетов](validation-v4.ru.md) и её [JSON](results-v4.json)
сравнивают четыре набора лимитов, включая общий NAT и смену адреса.
Универсальный набор лимитов не выбран.
[Проверка группировки вердиктов](validation-v3.ru.md) и её [JSON](results-v3.json)
сравнивают отдельную сборку с поштучной отправкой.
[Проверка предела копирования](validation-v2.ru.md) и её [JSON](results-v2.json)
описывают копирование 212 байт и ограничитель ядра.
[Первый отчёт VM](validation.ru.md) и [JSON](results.json) относятся
к прежней сборке.
В отчёте отдельно рассмотрены совместимость клиентов, некорректный трафик,
нагрузка на таблицу соединений и скорость. Проверялось клиентское ядро
в Linux; физические приложения Windows/macOS/Android/iOS в этих тестах
не запускались.
