# V43. Паузы приёма QEMU и режим AF_UNIX на стенде

[English](validation-v43.md) | Русский

Коммутатор стенда теперь поддерживает подключение QEMU через AF_UNIX. В двух прогонах дошли все 720 000 полезных UDP-пакетов и 200 ответов ping. Самая длинная пауза записи при непустой очереди коммутатора составила 25,2 мс. Прежнюю паузу в 4,77 с под диагностикой воспроизвести не удалось, поэтому её точная причина остаётся неизвестной.

## Где останавливался трафик

В неудачном прогоне v42 коммутатор продолжал получать шум, а B отправлял пакеты, хотя счётчик RX на A стоял. Гостевая программа продолжала снимать метрики. Задержка возникла после того, как данные поступили на коммутатор. Состояние сокетов Windows и QEMU и очереди Virtio в том прогоне не записывалось.

В v43 записывали остановки и возобновления чтения сокета QEMU, ожидания в его основном цикле и состояние Winsock при непустой очереди. В одном сбое между чтениями сокета A прошло 419,3 мс. Чтение было выключено суммарно не больше 2,23 мс за этот интервал. Ожиданий Windows или получения блокировки QEMU от 100 мс под нагрузкой журнал не показал. В другом прогоне запись на выход к клиенту стояла 859 мс при открытом TCP-окне, примерно 1,10 МБ неподтверждённых данных и повторных передачах. В отдельном прогоне все 23 попытки неблокирующего `send` без готовности от `select` вернули `WSAEWOULDBLOCK`. Прямая запись не снимала обратное давление. [Поля Windows TCP_INFO_v0](https://learn.microsoft.com/ru-ru/windows/win32/api/mstcpip/ns-mstcpip-tcp_info_v0)

Для калибровки локальную VM A остановили через QMP примерно на 758 мс. QEMU сообщил о паузе чтения на 752 мс, а коммутатор увидел нулевое TCP-окно. После запуска VM весь полезный UDP дошёл. Намеренная остановка дала другой сигнал, чем сбой с открытым окном.

## Прогоны AF_UNIX

Четыре гостевые VM Debian 13 работали на Windows под QEMU 11.1.3/WHPX. Каждой выделили одно ядро и 1024 МиБ без лимита CPU. Стенд подавал 25 000 шумовых пакетов/с с 16 адресов и 6000 полезных UDP-пакетов/с по 1200 байт. Те же клиенты меняли IP и NAT-порт при номинальном RTT 300 мс. Один прогон AF_UNIX прошёл после холодной загрузки. Настройки Virtio и размеры очередей остались прежними в обоих прогонах.

| Прогон | Нагрузка зачтена | Потери коммутатора | Потери UDP | Потери ping | Макс. RTT, мс |
|---|---|---:|---:|---:|---:|
| TCP, первый прогон с диагностикой | нет | 1542 | 1103 | 0 | 1272,734 |
| TCP, повтор с диагностикой | да | 0 | 0 | 0 | 1289,361 |
| TCP, журнал окна | да | 0 | 0 | 0 | 1233,277 |
| TCP, намеренная остановка QMP | да | 0 | 0 | 0 | 1301,221 |
| TCP, пассивный FIONREAD | нет | 3407 | 6193 | 2 | 1439,293 |
| TCP, пробная прямая запись | нет | 2382 | 4826 | 0 | 1402,563 |
| AF_UNIX, холодная загрузка | да | 0 | 0 | 0 | 1055,234 |
| AF_UNIX, повтор | да | 0 | 0 | 0 | 1200,147 |

Проверка нагрузки учитывает темп подачи и полноту измерений. Строка с остановкой QMP относится к калибровке. Незачтённые строки сохраняют наблюдавшиеся потери и исключены из сравнения фильтра.

AF_UNIX меняет и семейство сокета, и бэкенд QEMU с `socket` на `stream`. Такой режим убирает проверенное TCP-соединение, но по этому сравнению нельзя назвать конкретную функцию Windows или QEMU причиной исходной паузы. Публичная сборка коммутатора прошла тесты TCP и проверку передачи кадра через AF_UNIX. Диагностические образы и исходные захваты остались локальными. После испытаний восстановили обычный DNAT, проверили оба исходных профиля и выключили все четыре VM.
