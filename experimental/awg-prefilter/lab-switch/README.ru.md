# Локальный Ethernet-коммутатор QEMU для Windows

[English](README.md) | Русский

Этот помощник заменяет Python-коммутатор изолированного стенда фильтра
с четырьмя VM. Он обучается MAC-адресам и пересылает Ethernet-кадры через
TCP-соединения QEMU с префиксом длины. Слушает только `127.0.0.1`,
не создаёт сетевых адаптеров и не меняет маршруты, брандмауэр или VPN Windows.

Коммутатор работает на Windows-хосте стенда. Установщики VPS его не
развёртывают. Он не расшифровывает AWG и не подтверждает личность клиентов.

## Сборка и проверка

Нужны уже доступный в `PATH` Windows MinGW-w64 GCC и Python 3 для тестов.
Из этой папки в PowerShell:

```powershell
$lab = Join-Path $env:TEMP 'coldwire-native-switch'
New-Item -ItemType Directory -Force $lab | Out-Null
gcc -O2 -std=c11 -Wall -Wextra -Werror -static-libgcc native-switch.c -o "$lab\native-switch.exe" -lws2_32
python test_switch.py --binary "$lab\native-switch.exe" --workdir "$lab\selftest"
```

Оставьте assertions включёнными. Сборка с `NDEBUG` запрещена: проверки
и проверяемые вызовы API используют assertions. Тесты проверяют переход
через границу и переполнение очереди, вытеснение MAC и отключение узла,
частичные/объединённые чтения, максимальный кадр, непрозрачные данные,
обученный unicast, лимит соединений, счётчик шума и вытеснение старых
интервалов статистики. Отклонённое соединение может закрыться через EOF
или reset. Тест использует
localhost-порт 62591 и оставляет статистику в `--workdir`.

Запуск коммутатора стенда на порту 62590:

```powershell
& "$lab\native-switch.exe" 62590 "$lab\switch-stats.json"
```

Сетевые интерфейсы стенда в QEMU направляются в
`socket,id=lab,connect=127.0.0.1:62590`. Файл статистики явно задан как
выходной: раз в секунду он заменяется через временный файл. Используйте
путь, укладывающийся в Windows `MAX_PATH` и активную кодовую страницу:
помощник использует ANSI API для путей.

## QEMU на Windows: отправка кадра вместе с длиной

[Исследование v11](../validation-v11.ru.md) связало нестабильный темп
с путём отправки сокетов QEMU на Windows. Запасная реализация векторного
ввода-вывода записывает четыре байта длины и Ethernet-кадр отдельно.
[Патч](qemu-win32-single-write.patch) объединяет их в один буфер и одну
попытку `send()`, сохраняя обработку частичных записей и ошибок.
Меняется бинарник QEMU стенда; код коммутатора и VPS остаётся прежним.
TCP остаётся потоком байтов и может делить или объединять чтения.

Патч проверен с QEMU 11.1.3. Нужны уже настроенные исходники и каталог
сборки QEMU для Windows, а также MinGW-w64, использованный для сборки.
Из этой папки укажите свои пути к исходникам и сборке:

```powershell
$lab = Join-Path $env:TEMP 'coldwire-native-switch'
$qemuSource = 'C:\src\qemu-11.1.3'
$qemuBuild = 'C:\src\qemu-build'
$patch = (Resolve-Path '.\qemu-win32-single-write.patch').Path
git -C $qemuSource apply --check $patch
if ($LASTEXITCODE -ne 0) { throw 'Patch does not match this QEMU source' }
git -C $qemuSource apply $patch
if ($LASTEXITCODE -ne 0) { throw 'Patch application failed' }
python test_qemu_stream.py --source "$qemuSource\net\socket.c" --workdir "$lab\stream-test"
if ($LASTEXITCODE -ne 0) { throw 'Stream regression test failed' }
ninja -C $qemuBuild qemu-system-x86_64.exe
if ($LASTEXITCODE -ne 0) { throw 'QEMU build failed' }
```

Остановите VM стенда перед заменой их бинарника. Запускайте их с новой
сборкой, сохраняя `TCP_NODELAY` на обоих концах. Команды предполагают
готовую среду сборки QEMU; они не устанавливают её зависимости и не
включают прежние исправления совместимости WHPX этого стенда.

Регрессионный тест компилирует настоящую функцию `net_socket_receive`
с ограниченными подставными операциями ввода-вывода. Он проверяет одну
запись полного кадра, точные байты, частичные повторы, `EAGAIN`, нулевую
запись, фатальные ошибки, пустую/максимальную нагрузку и освобождение
памяти. Исходная Windows-реализация нарушает проверку одной записи.
Тест не использует сокеты или ресурсы VM.

## Измерение ICMP с явным ожиданием

[v12](../validation-v12.ru.md) показал, что старый `ping -c100 -i0.02 -W1`
может завершиться до прихода последнего задержанного ответа.
[ICMP-помощник](icmp-probe.py) отправляет ровно 100 IPv4-запросов выходу
стенда `10.8.1.1`, с нагрузкой 56 байт через 20 мс. Бюджет ответа явно
равен секунде; результат записывается в JSON. Интерфейсы и маршруты не меняются,
на VPS и физических клиентах помощник не устанавливается.

Самопроверка работает в Python 3 без сетевого доступа. Оставьте assertions
включёнными; `python -O` не поддерживается. Режим VM требует Linux,
root с `CAP_NET_RAW` и существующее пространство имён стенда. Из этой папки:

```bash
python3 icmp-probe.py --self-test
sudo ip netns exec pf-client1 python3 icmp-probe.py --vm-test
```

Нулевой код выхода означает, что все 100 ответов пришли в пределах
бюджета. JSON содержит номера пропусков, поздние ответы и дубликаты.
Проверяйте результат и stderr: ошибка запуска/сокета означает неудачное
измерение, а не сетевые потери. Живые контроли приняли задержанный
последний ответ и обнаружили намеренный сброс запроса. Помощник
не заменяет проверку CPU всей VM, темпа источника и захват пакетов.

## Ограничения и наблюдения

Коммутатор принимает четыре соединения и хранит до 64 MAC-адресов.
При заполнении таблицы замещается самая старая запись. Неизвестный unicast
и multicast передаются остальным участникам; известный unicast своему
адресату. Это поведение Ethernet без политики контроля доступа.

На участника выделены входной буфер 256 КиБ и выходное кольцо 4 МиБ.
При заполнении кольца копия для этого адресата отбрасывается, растёт
`dropped`. Длина выше 65 536 байт закрывает отправляющее соединение;
кадры короче 14 байт игнорируются. Байты допустимых кадров и порядок
в очереди каждого адресата сохраняются. У принятых сокетов включён
`TCP_NODELAY`.

Счётчик шума распознаёт только тестовый поток: IPv4 без опций,
UDP из `192.168.76.40` с любым портом источника в `192.168.76.10:32497`,
длина UDP 264.
Остальной трафик пересылается обычным образом и в этот счётчик не входит.
Проверка адресов здесь служит измерению; это не брандмауэр и не список
допущенных клиентов.

Метки поступления используют QPC и последние 4096 непустых интервалов
по 100 мс. При заполнении вытесняется самый старый: сохраняется не менее
409,6 секунды активной истории. Общие счётчики кадров и время первого/последнего
прихода продолжают накапливаться. Для более длинного теста сохраняйте
интервалы до их вытеснения. Это заменяет прежнюю проверку на 20 000
интервалов, которая остановила коммутатор в [серии v19](../validation-v19.ru.md).
`max_pending_age_ns` измеряет период непустой
очереди, без оценки задержки отдельного пакета. Счётчики частичных
и заблокированных отправок описывают сокеты процесса, без измерения
всех буферов внутри QEMU и Windows.

Счётчики порта накапливаются для его слота до перезапуска, а MAC помечает
текущего участника. Для учёта всего прогона используются общие счётчики.

Это лабораторный инструмент. Его тесты не доказывают пригодность для
рабочей сети или максимальную частоту пакетов. Вместе проверяйте реальный
темп отправки и поступления, полезную скорость, потери и CPU каждой VM.
