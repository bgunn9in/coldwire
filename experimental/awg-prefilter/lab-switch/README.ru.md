# Локальный Ethernet-коммутатор QEMU для Windows

[English](README.md) | Русский

Этот помощник заменяет Python-коммутатор изолированного стенда фильтра
с четырьмя VM. Он запоминает MAC-адреса и пересылает кадры QEMU с префиксом
длины через локальный сокет AF_UNIX или TCP на `127.0.0.1`. Он не создаёт
сетевых адаптеров и не меняет маршруты, брандмауэр или VPN Windows.

Коммутатор работает на Windows-хосте стенда. Установщики VPS его не
развёртывают. Он не расшифровывает AWG и не подтверждает личность клиентов.

## Сборка и проверка

Нужны уже доступный в `PATH` Windows MinGW-w64 GCC и Python 3 для тестов.
Из этой папки в PowerShell:

```powershell
$lab = Join-Path $env:TEMP 'coldwire-native-switch'
New-Item -ItemType Directory -Force $lab | Out-Null
gcc -O2 -std=c11 -Wall -Wextra -Werror -static-libgcc native-switch.c -o "$lab\native-switch.exe" -lws2_32
python test_switch.py --binary "$lab\native-switch.exe" --workdir "$lab\selftest"
```

Оставьте assertions включёнными. Сборка с `NDEBUG` запрещена: проверки
и проверяемые вызовы API используют assertions. Тесты проверяют переход
через границу и переполнение очереди, вытеснение MAC и отключение узла,
частичные/объединённые чтения, максимальный кадр, непрозрачные данные,
обученный unicast, лимит соединений, счётчик шума и вытеснение старых
интервалов статистики. Отклонённое соединение может закрыться через EOF
или reset. Тест использует
localhost-порт 62591 и оставляет статистику в `--workdir`.

## Подключение интерфейсов стенда

На Windows с поддержкой AF_UNIX используйте этот сокет с бэкендом QEMU
`stream`. При 25 000 фоновых пакетов/с коммутатор передал все кадры в двух
прогонах AF_UNIX. В одном прогоне TCP на том же бэкенде передача остановилась
на несколько секунд и выходная очередь переполнилась.

Запустите коммутатор до QEMU. Выберите свободный путь в каталоге стенда.
Полный путь должен занимать не больше 107 байт.

```powershell
& "$lab\native-switch.exe" 'unix:C:\lab\cw.sock' "$lab\switch-stats.json"
```

Для интерфейса данных задайте `-netdev stream,id=lab,addr.type=unix,addr.path=C:/lab/cw.sock`.
Сохраните устройство Virtio с параметром `netdev=lab` и интерфейс управления.
Перед повторным использованием пути дождитесь остановки QEMU и коммутатора,
затем удалите сокет стенда.

Для связи через локальный TCP запустите коммутатор на порту 62590.

```powershell
& "$lab\native-switch.exe" 62590 "$lab\switch-stats.json"
```

Укажите `-netdev stream,id=lab,addr.type=inet,addr.host=127.0.0.1,addr.port=62590`.
Значение `tcp_nodelay` равно `true` для TCP и `false` для AF_UNIX.

Коммутатор заменяет файл статистики раз в секунду. Уложите путь в
Windows `MAX_PATH` и активную кодовую страницу. В статистике каждого
соединения `output_drops` считает кадры, которые не поместились в выходную
очередь. `max_queued_send_gap_ns` показывает самый длинный промежуток без
записи в сокет при наличии данных в очереди. `max_pending_age_ns` измеряет
время, в течение которого очередь оставалась непустой.

## Запись времени коммутатора и хоста

Для нагрузочного прогона пишите статистику, pcap и stderr коммутатора на
быстрый локальный диск. JSON и pcap пишутся в процессе пересылки. В
контроле v46 после переноса вывода на отдельный диск запись JSON укладывалась
в порог журнала 20 мс. [Замеры v46](../validation-v46.ru.md)

```powershell
$scratch = 'C:\lab\switch-output'
$tap = Join-Path $scratch 'pcap'
New-Item -ItemType Directory -Force $tap | Out-Null
& "$lab\native-switch.exe" 'unix:C:\lab\cw.sock' "$scratch\switch-stats.json" $tap 2> "$scratch\switch.log"
```

Третий аргумент включает захват. Для каждого запуска используйте новый
каталог. Когда лабораторный клиент использует NAT-порт 42501,
коммутатор захватывает восемь секунд трафика тестового туннеля и канала
управления. При следующем совпадении после закрытия откроется новый
захват. В захвате может быть VPN-трафик. Храните его локально.
Перед разбором проверьте `tap_errors` и совпадение `tap_closed` с
`tap_sequence`. Счётчик `noise_output_drops` показывает, сколько
фоновых кадров из тестовой нагрузки отброшено на каждом выходе.

Для замера обратного пути из v51 добавьте `--return-headers` после
каталога захвата. Коммутатор также записывает UDP в направлении A →
клиент и сохраняет до 96 байт каждого захваченного кадра. В PCAP остаются
исходная длина кадра и метка времени хоста. Если декодеру нужны пакеты целиком, запустите захват без этого флага. [Замеры v51](../validation-v51.ru.md)

В stderr попадают длинные интервалы опроса, пересылки и записи статистики
с метками QPC. Интервал отбрасываний записывается после возобновления
передачи на соответствующем выходе. Для замеров TCP нужны заголовки
Winsock с `SIO_TCP_INFO`. С проверенными заголовками MinGW-w64 замеры
включаются флагом `-DNTDDI_VERSION=0x0A000003` в команде GCC выше.
Пересылка AF_UNIX и счётчики очередей работают и без этого флага.

[Диагностический патч QEMU](qemu-win32-stream-observer.patch) для 11.1.3
записывает интервалы между чтениями, паузы обработчика Virtio и ожидания
главного цикла. Проверьте и примените его из каталога исходников QEMU
командами `git apply --check` и `git apply`, затем соберите QEMU по примеру
ниже. Чтобы включить независимый датчик приёмника, задайте
`CW45_STREAM_RX_LOG` в окружении наблюдаемого процесса QEMU. Используйте
новый локальный файл для каждого процесса. Патч работает с `stream` на
обоих семействах сокетов. [Замеры приёмника](../validation-v45.ru.md)

Запустите [наблюдатель часов хоста](host-clock.py) в отдельном процессе
Windows на время прогона. Он сохраняет замеры по истечении указанного
времени или после Ctrl+C. Укажите новый выходной файл.

```powershell
python host-clock.py "$scratch\host-clock.json" --seconds 180
```

## BQL и планировщик Windows

Для стенда на QEMU 11.1.3 сначала примените патч наблюдения за `stream`,
затем [патч диагностики BQL](qemu-win32-bql-observer.patch). Проверьте и
примените оба из каталога исходников QEMU. Патч BQL записывает
идентификатор главного потока и интервалы захвата и владения блокировкой
SRW длительностью от 5 мс. Запись о владении появляется при освобождении
блокировки. Метки времени берутся из QPC.

Соберите два помощника ETW из этого каталога с помощью MinGW-w64.
Создайте новый рабочий каталог на локальном диске с местом для трассы.

```powershell
$scratch = 'C:\lab\bql-trace-01'
New-Item -ItemType Directory -Path $scratch | Out-Null
gcc -O2 -Wall -Wextra -Werror -municode scheduler-record.c -o "$scratch\scheduler-record.exe" -ladvapi32
gcc -O2 -Wall -Wextra -Werror -municode scheduler-read.c -o "$scratch\scheduler-read.exe" -ladvapi32
```

После загрузки VM и до начала нагрузки запустите запись из PowerShell
с правами администратора. Используйте тот же путь `$scratch`.

```powershell
& "$scratch\scheduler-record.exe" "$scratch\scheduler.etl" "$scratch\stop.request" 180
```

Помощник записывает события планировщика хоста Windows. Сырые ETL
храните локально. Запись завершится по таймеру, при достижении 2 ГиБ
или при появлении файла `stop.request`. Чтобы закончить раньше, создайте
этот файл из другого терминала. Проверьте статус `STOP` и счётчики потерь.
Используйте только интервалы, покрытые трассой. Для автоматизации после
длительности можно передать путь к маркеру запуска и журналу статуса.

Разбирайте по одной VM. Укажите журнал stderr QEMU с записями
`CW47 main` и `CW47 bql`. Для перенаправления вывода в примере ниже
используйте PowerShell 7.

```powershell
$log = Join-Path $scratch 'entry-qemu.log'
$ids = Join-Path $scratch 'entry-threads.txt'
$csv = Join-Path $scratch 'entry-scheduler.csv'
python bql-report.py threads $log | Set-Content -Encoding ascii $ids
& "$scratch\scheduler-read.exe" "$scratch\scheduler.etl" $ids > $csv
python bql-report.py report $csv $log
```

Чтобы отметить vCPU, передайте `--vcpu-tid` со значением `thread-id`
из `query-cpus-fast` для этой VM. Для окна нагрузки передайте
`--start-ns` и `--end-ns` со значениями `noise_first_ns` и
`noise_last_ns` коммутатора. В отчёте для завершённых захватов есть
время исполнения, готовности, ожидания и интервалы с неизвестным
состоянием, а также совпадающие интервалы владения BQL.
[Замеры и ограничения](../validation-v47.ru.md)

## Обращения к устройствам и стеки ожидания ETW

Примените [патч MMIO](qemu-win32-mmio-observer.patch) к тому же дереву
QEMU 11.1.3, что и патч BQL. Строка `CW48 mmio` содержит регион, тип
устройства, адрес, направление и размер медленного обращения с захватом
BQL. Для x86 адрес может быть номером порта ввода-вывода. Адрес из одних
единиц означает, что для обращения доступно только смещение в регионе.
QEMU пишет эту строку после освобождения BQL.

Для записи запуска откройте PowerShell с повышенными правами и используйте
`xperf` из Windows Performance Toolkit. Выберите рабочий каталог за
пределами репозитория. Если NT Kernel Logger уже принадлежит другому
приложению, оставьте его работать. Запустите VM стенда после включения
трассировки и завершите запись по окончании запуска.

```powershell
if ((xperf -loggers) -match '^\s*Logger Name\s*:\s*NT Kernel Logger\s*$') {
    throw 'NT Kernel Logger is already running'
}
xperf -on PROC_THREAD+LOADER+CSWITCH+DISPATCHER+DISK_IO+DISK_IO_INIT+HARD_FAULTS -stackwalk CSwitch -ClockType PerfCounter -f "$scratch\startup.etl" -BufferSize 256 -MinBuffers 128 -MaxBuffers 384 -MaxFile 4096
if ($LASTEXITCODE -ne 0) { throw 'Could not start the trace' }
try { Read-Host 'Start the lab VMs in another terminal. Press Enter to stop the trace' }
finally { xperf -stop }
```

Запишите в файл `$ids` TID главного потока и vCPU, по одному номеру на
строку. TID главного потока указан в `CW47 main`. TID vCPU можно получить
из `thread-id` ответа QMP `query-cpus-fast`, когда монитор станет доступен.
Используйте декодер, собранный в предыдущем разделе.

```powershell
& "$scratch\scheduler-read.exe" "$scratch\startup.etl" $ids --details > "$scratch\startup.csv"
if ($LASTEXITCODE -ne 0) { throw 'Incomplete ETW decode' }
python mmio-report.py "$scratch\startup.csv" "$qemuLog" $vcpuTid > "$scratch\mmio.json"
```

Используйте PowerShell 7 для перенаправления в UTF-8. Без `--details`
декодер сохраняет прежний формат CSV. С этим флагом он добавляет стеки,
диапазоны образов, события HardFault и завершения дисковых операций.
Отчёт берёт стек при следующем переключении на тот же TID и переводит
адреса кадров стека в RVA. Для кадра QEMU прибавьте RVA к предпочтительному
`ImageBase` из PE и передайте адрес в `addr2line -f -e` с диагностическим
бинарником с отладочными символами. Параметр `-trace enable=pci_cfg_write`
показывает адрес устройства и регистр PCI. Используйте его для определения
устройства. Запись журнала PCI может сама продлить удержание BQL.

Храните ETL, CSV и JSON замеров локально. См. [отчёт v48](../validation-v48.ru.md).

## Буфер COM1 на хосте

Чтобы последовательный порт не писал на диск во время теста, замените
`-serial file:PATH` в параметрах запуска каждой VM стенда.

```text
-chardev ringbuf,id=lab-com1,size=1048576 -serial chardev:lab-com1
```

В скрипте запуска на Python ту же замену делает
[`qemu_com1.with_ringbuf(argv)`](qemu_com1.py). Используйте QMP на
loopback. После нагрузки и остановки ETW выгрузите буфер в новый файл
до выключения VM. В примере 62622 — локальный порт QMP, а `$scratch` —
каталог за пределами репозитория.

```powershell
python qemu_com1.py 62622 "$scratch\entry-com1.log"
```

При заполнении буфер объёмом 1 МиБ перезаписывает старые байты.
Прочитанные данные удаляются из буфера. Храните журналы вместе с
локальными ETL. Сравнение с файловым COM1 приведено в [отчёте v49](../validation-v49.ru.md).
[В серии v50](../validation-v50.ru.md) сравнение повторили в трёх чередующихся парах при 25 000 пакетов/с.

## QEMU на Windows: отправка кадра вместе с длиной

[Исследование v11](../validation-v11.ru.md) связало нестабильный темп
с путём отправки сокетов QEMU на Windows. Запасная реализация векторного
ввода-вывода записывает четыре байта длины и Ethernet-кадр отдельно.
[Патч](qemu-win32-single-write.patch) объединяет их в один буфер и одну
попытку `send()`, сохраняя обработку частичных записей и ошибок.
Патч применяется к старому бэкенду `socket`. Настройка `stream` выше работает
без него.
TCP остаётся потоком байтов и может делить или объединять чтения.

Патч проверен с QEMU 11.1.3. Нужны уже настроенные исходники и каталог
сборки QEMU для Windows, а также MinGW-w64, использованный для сборки.
Из этой папки укажите свои пути к исходникам и сборке:

```powershell
$lab = Join-Path $env:TEMP 'coldwire-native-switch'
$qemuSource = 'C:\src\qemu-11.1.3'
$qemuBuild = 'C:\src\qemu-build'
$patch = (Resolve-Path '.\qemu-win32-single-write.patch').Path
git -C $qemuSource apply --check $patch
if ($LASTEXITCODE -ne 0) { throw 'Patch does not match this QEMU source' }
git -C $qemuSource apply $patch
if ($LASTEXITCODE -ne 0) { throw 'Patch application failed' }
python test_qemu_stream.py --source "$qemuSource\net\socket.c" --workdir "$lab\stream-test"
if ($LASTEXITCODE -ne 0) { throw 'Stream regression test failed' }
ninja -C $qemuBuild qemu-system-x86_64.exe
if ($LASTEXITCODE -ne 0) { throw 'QEMU build failed' }
```

Остановите VM стенда перед заменой их бинарника. Запускайте их с новой
сборкой, сохраняя `TCP_NODELAY` на обоих концах. Команды предполагают
готовую среду сборки QEMU; они не устанавливают её зависимости и не
включают прежние исправления совместимости WHPX этого стенда.

Регрессионный тест компилирует настоящую функцию `net_socket_receive`
с ограниченными подставными операциями ввода-вывода. Он проверяет одну
запись полного кадра, точные байты, частичные повторы, `EAGAIN`, нулевую
запись, фатальные ошибки, пустую/максимальную нагрузку и освобождение
памяти. Исходная Windows-реализация нарушает проверку одной записи.
Тест не использует сокеты или ресурсы VM.

## Измерение ICMP с явным ожиданием

[v12](../validation-v12.ru.md) показал, что старый `ping -c100 -i0.02 -W1`
может завершиться до прихода последнего задержанного ответа.
[ICMP-помощник](icmp-probe.py) отправляет ровно 100 IPv4-запросов выходу
стенда `10.8.1.1`, с нагрузкой 56 байт через 20 мс. Бюджет ответа явно
равен секунде; результат записывается в JSON. Интерфейсы и маршруты не меняются,
на VPS и физических клиентах помощник не устанавливается.

Самопроверка работает в Python 3 без сетевого доступа. Оставьте assertions
включёнными; `python -O` не поддерживается. Режим VM требует Linux,
root с `CAP_NET_RAW` и существующее пространство имён стенда. Из этой папки:

```bash
python3 icmp-probe.py --self-test
sudo ip netns exec pf-client1 python3 icmp-probe.py --vm-test
```

Нулевой код выхода означает, что все 100 ответов пришли в пределах
бюджета. JSON содержит номера пропусков, поздние ответы и дубликаты.
Проверяйте результат и stderr: ошибка запуска/сокета означает неудачное
измерение, а не сетевые потери. Живые контроли приняли задержанный
последний ответ и обнаружили намеренный сброс запроса. Помощник
не заменяет проверку CPU всей VM, темпа источника и захват пакетов.

## Несколько источников шума

Linux-[генератор шума](noise-multi-source.c) привязывает сокеты к существующим
адресам одноразовой VM `kit-restore`, до 16 адресов и 8192 UDP-сокетов. Он сообщает
число успешных отправок по каждому IP. Параметр скорости задаёт общий темп всех
источников. Назначение фиксировано: лабораторный вход `192.168.76.10:32497`;
выбрать внешний адрес нельзя.

Сборка и офлайн-проверка в Linux-госте:

```bash
gcc -O2 -std=c11 -Wall -Wextra -Werror noise-multi-source.c -o noise-multi-source
./noise-multi-source --self-test
```

Для отправки нужны hostname `kit-restore`, настроенные адреса начиная с
`192.168.76.40` и готовый файл образца на 256 байт в `/root/prefilter`.
Лабораторный пример ниже отправляет суммарно 25 000 пакетов/с на 70 секунд,
пачками по 4096, через 64 сокета с 16 адресов:

```bash
./noise-multi-source 25000 70 4096 64 captured-prefix 16
```

V30 добавляет до 8192 сокетов для проверки conntrack, длительность до 900
секунд и необязательные начальные адрес/порт. Отдельные процессы могут
использовать непересекающиеся потоки с независимым расписанием пачек.
Генератор поднимает собственный мягкий предел дескрипторов в границах
действующего жёсткого. Адреса остаются в `192.168.76.40`-`.55`, назначение
фиксировано.
Расписание должно помещаться в 16384 записи пачек; превышение отклоняется
до начала отправки.

```bash
./noise-multi-source 25000 70 4096 8192 captured-prefix 16
./noise-multi-source 6250 300 257 16 captured-prefix 4 40 40000
```

Генератор не создаёт адреса и ключи. [Исследование v28](../validation-v28.ru.md)
сверяет отправки по каждому источнику с независимыми счётчиками коммутатора.

## Компактный журнал номеров UDP

Лабораторный [сборщик](udp-capture.py) записывает каждый фактический счётчик
iperf UDP и время захвата, включая отдельные счётчики внутри GSO. Тела
пакетов не сохраняются. Допустима нагрузка 128, 512 или 1200 байт.
Фрагменты UDP и обрезанный захват отклоняются. Размер нагрузки должен
помещаться в MTU исходного профиля; менять MTU клиента ради теста не нужно.

```bash
python3 udp-capture.py --self-test
sudo install -d -m700 /root/prefilter/pingtrace/smoke
# Одноразовая kit-client; сборщик должен быть доступен по этому пути:
sudo ip netns exec pf-client1 python3 /path/to/udp-capture.py pf1 1200 /root/prefilter/pingtrace/smoke/udp.seq
```

Остановка через SIGINT. Сохраните признак завершения в `.seq.meta.json`
и отчёт tcpdump о потерях из stderr; незавершённые файлы не подтверждают
доставку. Нужны root, имя `kit-client` или `kit-exit` и путь внутри
`/root/prefilter/pingtrace`. Используется установленный tcpdump с immediate
mode, снимком 65535 байт и кольцом захвата 64 МиБ. В v30 наборы реальных
счётчиков и временные отметки сверены с отдельным полным захватом на меньшей
скорости калибровки. Эти закрытые файлы исключены из Git.

## Пределы коммутатора

Коммутатор принимает четыре соединения и хранит до 64 MAC-адресов.
При заполнении таблицы замещается самая старая запись. Неизвестный unicast
и multicast передаются остальным участникам; известный unicast своему
адресату. Это поведение Ethernet без политики контроля доступа.

На участника выделены входной буфер 256 КиБ и выходное кольцо 4 МиБ.
При заполнении кольца копия для этого адресата отбрасывается, растёт
`dropped`. Длина выше 65 536 байт закрывает отправляющее соединение;
кадры короче 14 байт игнорируются. Байты допустимых кадров и порядок
в очереди каждого адресата сохраняются. У принятых сокетов включён
`TCP_NODELAY`.

Счётчик шума распознаёт только тестовый поток: IPv4 без опций,
UDP из диапазона `192.168.76.40`-`192.168.76.55` с любым портом источника в `192.168.76.10:32497`,
длина UDP 264.
Остальной трафик пересылается обычным образом и в этот счётчик не входит.
Проверка адресов здесь служит измерению; это не брандмауэр и не список
допущенных клиентов.
Ограниченный словарь `noise_source_frames` содержит по одному общему счётчику
для каждого из шестнадцати адресов. Разность снимков до/после проверяет нагрузку.

Метки поступления используют QPC и последние 4096 непустых интервалов
по 100 мс. При заполнении вытесняется самый старый: сохраняется не менее
409,6 секунды активной истории. Общие счётчики кадров и время первого/последнего
прихода продолжают накапливаться. Для более длинного теста сохраняйте
интервалы до их вытеснения. Это заменяет прежнюю проверку на 20 000
интервалов, которая остановила коммутатор в [серии v19](../validation-v19.ru.md).
`max_pending_age_ns` измеряет период непустой
очереди, без оценки задержки отдельного пакета. Счётчики частичных
и заблокированных отправок описывают сокеты процесса, без измерения
всех буферов внутри QEMU и Windows.

Счётчики порта сбрасываются при отключении. MAC обозначает текущего
участника. Общие счётчики сохраняют итоги прогона.

Это лабораторный инструмент. Его тесты не доказывают пригодность для
рабочей сети или максимальную частоту пакетов. Вместе проверяйте реальный
темп отправки и поступления, полезную скорость, потери и CPU каждой VM.

## Независимая полезная нагрузка UDP

`udp-load.c` создаёт нагрузку в локальных Linux-VM `kit-client` и `kit-exit`.
Он отправляет ровно 360 000 пакетов с номерами за 60 секунд при темпе 6000/с.
Приёмник работает 67 секунд, считает уникальные пакеты, дубликаты и неверные
сообщения. Допустимы размеры 128 и 1200 байт, только стендовые адреса
`10.8.1.1` и `10.8.1.2` и UDP-порт 5201. TCP-канала управления нет, поэтому
им можно измерять намеренные обрывы связи. Это тестовое приложение;
бинарники и профили VPN остаются прежними.

```sh
cc -O2 -std=c11 -Wall -Wextra -Werror udp-load.c -o udp-load
./udp-load --self-test
```

Сначала запустите `./udp-load recv 10.8.1.1 128` от root в `kit-exit`, затем
`./udp-load send 10.8.1.2 10.8.1.1 128` от root в VPN-пространстве клиента.
Для download поменяйте адреса отправителя и приёмника местами и используйте
размер 1200. Assertions должны оставаться включёнными. Приёмник запрашивает
собственный буфер 4 МиБ через `SO_RCVBUFFORCE` (Linux сообщает 8 МиБ), не меняя
общие sysctl. Это устраняет потери всплеска восстановления в маленьком буфере
стендового приложения. Буферы реальных приложений всё ещё могут переполняться.
Сверяйте захват внутреннего интерфейса с результатом приёмника. Поле
`missing_by_scheduled_second` содержит 60 чисел пропусков. Приёмник вычисляет
их по номерам пакетов после прогона. Нулевой элемент охватывает номера с 1
по 6000. Группы следуют расписанию отправителя и не содержат отметок времени
захвата. По ним можно проверить доставку без захвата UDP. Подробнее в [v36](../validation-v36.ru.md).
