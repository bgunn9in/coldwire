# Краткий допуск потока с подтверждением от выходного узла

[English](README.md) | Русский

Этот эксперимент даёт потоку авторизованного клиента временный обход
общего лимита неизвестного трафика и NFQUEUE на входном узле. Приложения,
профили и ключи клиентов AWG 3.1 остаются прежними. Публичный IP и порт NAT
могут меняться. На обоих серверах нужен дополнительный код; обычные
установщики COLDWIRE его не устанавливают и не включают.
[Проверка восстановления ответов](../validation-v22.ru.md) добавляет отдельную
опцию истории зашифрованных ответов B за 500 мс. Шесть финальных прогонов
прошли без сетевых потерь UDP и опоздавших проб, CPU учитывается без порога.
Опция по умолчанию выключена; повторяющиеся сетевые пакеты не проверены
против DPI. [Отложенное восстановление](../validation-v24.ru.md) добавляет
один ограниченный снимок для быстрых смен адреса. [Продолжение v25](../validation-v25.ru.md)
сохраняет и дополняет его между попытками. Предыдущая
[проверка границ](../validation-v23.ru.md) изучает большой RTT и позднее обнаружение пути.
Прежние результаты: [продолжение при RTT 300 мс](../validation-v21.ru.md),
[исходные тесты WAN](../validation-v20.ru.md), [проверка смены адреса в локальной сети](../validation-v19.ru.md)
и [измерения v18](../validation-v18.ru.md).

## Как появляется допуск

1. A пропускает неизвестный поток через ограничитель и прежний фильтр
   Header Protection/MAC1. Эти проверки не авторизуют клиента.
2. Модифицированный приёмник AWG на B отправляет локальное событие после
   расшифровки transport-пакета, проверки повтора и допустимого внутреннего
   адреса отправителя. Подтверждённый keepalive тоже может дать событие.
   Пакет, похожий на рукопожатие, и состояние conntrack такого
   подтверждения не дают.
3. A читает исходные IP/порт, идентификатор conntrack и порт после NAT из
   своей таблицы соединений. Запрашивает у B подтверждение порта со свежим
   случайным 128-битным nonce. B должен увидеть новый проверенный
   transport-пакет после получения запроса. Обе временные отметки
   сравниваются по монотонным часам B; синхронизация часов серверов для
   этой проверки не нужна.
4. Ответ идёт по соединению TLS 1.3 с взаимной проверкой сертификатов. A
   проверяет nonce, срок запроса, порядок событий и заново сверяет
   conntrack. В nftables появляется допуск на десять секунд для
   `исходный IPv4 . исходный UDP-порт . идентификатор conntrack`.
5. Активный трафик может продлевать допуск. Подтверждённый новый поток того
   же клиента заменяет старый. Неактивный допуск истекает. При потере
   управляющего соединения A сбрасывает состояние; остановка процесса не
   мешает ядру удалить допуск по таймеру.

Интерфейс, адрес назначения и порт VPN в лабораторных правилах фиксированы.
Этот прототип не служит универсальным кешем для разных назначений. Порт
после NAT читается из conntrack, а не предполагается равным клиентскому.

A опрашивает conntrack каждые 100 мс и сразу применяет принятое
подтверждение к nftables. B может выдавать свежее событие прежнего адреса
каждые 50 мс; TLS-поток использует `TCP_NODELAY`. B выбирает адрес
и события подтверждения по наибольшему принятому transport-счётчику
текущей пары ключей; при смене текущей пары счётчик начинается заново.
Запоздавшие корректные данные могут быть доставлены, но не выбирают
старый адрес. При выключенном восстановлении ответы, уже отправленные
в исчезнувшее сопоставление NAT, остаются потерянными.

A получает хеш открытого ключа подтверждённого клиента. Ключи VPN-сессии и
закрытые ключи клиентов остаются вне A. Управляющее соединение использует
отдельные сертификаты. Закрытый Unix-сокет принимает учётные данные root
и передаёт события без пользовательской нагрузки: монотонное время,
наблюдаемые IP/порт, идентификатор клиента и счётчик transport-пакета.
B по-прежнему криптографически проверяет каждый пакет VPN.

## Ограничения и границы защиты

Текущие правила ограничивают неизвестный трафик до 1500 пакетов/с с burst
4096 на исходный IPv4, затем применяют общий бюджет 6000/с с burst 1024.
Больший начальный запас покрывает измеренное ожидание свежего подтверждения
при смене потока. Он пополняется с прежней длительной скоростью и не
выделяет буфер пакетов. Достаточно долгая задержка всё ещё может его исчерпать.
После проверки заголовка для неподтверждённых initiation/response/cookie
действует отдельный лимит: 20/с с burst 8 на исходный IPv4, затем 100/с
с burst 16 суммарно. Больший запас данных не должен одновременно заполнять
обработчик рукопожатий B. Класс берётся из раскрытого типа сообщения AWG,
а не из длины пакета или совпадения с конкретным образцом шума.
Динамический набор содержит не более 4096 адресов; неактивные записи
истекают через пять секунд. Если запись создать нельзя, новый неизвестный
трафик отбрасывается. Один источник не получает новые порции бюджета за
счёт множества портов. Адреса берутся из пакетов, постоянный IP клиента и
список разрешённых клиентских IP не нужны. Подтверждённые потоки обходят
оба этих лимита.

Набор допусков ограничен 4096 потоками. Вспомогательные процессы держат не
более 128 незавершённых запросов, создают до шестнадцати за один такт и
удаляют запросы старше трёх секунд. Размеры истории, состояния клиентов и
буферов соединения тоже ограничены. В C-фильтре сохранены очередь 4096,
копирование 212 байт и группировка индивидуальных вердиктов.
Сохраняются ограничения фильтра `S1-S4=12`, `H1-H4=1,2,3,4`. Внешний
транспорт IPv6 не поддерживается.

Допуск относится к IP/порту/conntrack, поэтому не проверяет подлинность
каждого следующего пакета на A. Отправитель, способный подделать уже
допущенные IP и порт, может попасть в обходной путь до истечения допуска.
В стенде это воспроизведено одним пакетом с изменённым шифротекстом: B
отклонил его, допуск не продлился. Злоупотребления зарегистрированного
клиента, внедрение пакетов на пути, подмена адресов, распределённые
источники и насыщение внешнего канала требуют отдельной защиты.

До подтверждения клиенты за одним публичным IP делят бюджет неизвестного
источника. Новое соединение и сменившийся поток должны получить свежее
подтверждение; в этот период возможна потеря пакетов. В v18 сохранены
исходные переходные потери; v19 сравнивает новые запасы с прежними и
проверяет холодные подключения.
Клиенты за одним исходным IP также делят бюджет управляющих сообщений.
Много одновременных клиентов, переполнение наборов и адаптивные атаки
с cookie/MAC2 не проверялись.
Превышение предела 4096 кандидатов conntrack может сбросить уже выданные
допуски и помешать клиентам. Этот предел ограничивает память, но не
предотвращает такое исчерпание состояния.

Неизвестные потоки сохраняют строгую политику отбрасывания I1/Jc.
Действующий допуск обходит фильтр для своего потока, включая маскировочные
пакеты. Формат клиентского трафика не менялся; получившаяся маскировка на
участке от A до B не проверялась средствами DPI.

## Дополнительное восстановление обратных пакетов

В модифицированном бинарнике есть отдельная лабораторная опция,
выключенная по умолчанию: `COLDWIRE_LAB_RETURN_REPLAY=1`. Ей также нужна
прежняя настройка `COLDWIRE_LAB_PROOF_SOCKET`. Установщики обе опции
не включают.

B копирует исходящие зашифрованные transport-пакеты в общее кольцо.
В нём до 8192 пакетов и 8 МиБ шифротекста, плюс фиксированные метаданные.
Для повторной отправки подходят пакеты моложе 500 мс; очистка при простое
работает каждые 100 мс. Хранятся хеш открытого ключа клиента и скалярные
поля эпохи пары ключей. Открытые данные, ключи сессии и указатели на пары
ключей не сохраняются.

После свежего transport-пакета с допустимым внутренним адресом и новым
внешним адресом B применяет этот адрес до снимка кеша. Отправитель
сохраняет каждый зашифрованный пакет перед чтением его назначения;
созданные после снимка пакеты уже идут новым путём. B может повторить
туда шифротекст этого клиента и текущей эпохи. Одна попытка берёт
до 8192 пакетов и 2 МиБ в исходном порядке.
На клиента допускается не более одной попытки за 250 мс, включая пустой
немедленный поиск, суммарно не более одной непустой попытки за 250 мс.
Одновременно отправляется только одна копия. Обычное обновление адреса
продолжается во время ожидания. Прежний фильтр повторов клиента
отбрасывает уже полученные копии.

После немедленной попытки B сохраняет выбранный шифротекст без повторного
копирования данных. Трафик без смены адреса не разрешает новую попытку.
Смена, заблокированная cooldown или занятой отправкой, тоже может создать
снимок из обычного кольца. Общий предел снимков: 16 клиентов, 8192 пакетов
и 2 МиБ. Хранятся шифротекст, хеш открытого ключа, скалярные поля ключевой
эпохи/порядка и строка адреса. Свежая проверенная смена меняет назначение
и добавляет более новые подходящие ответы из кольца в пределах тех же
бюджетов. Локальный номер вставки исключает повторное копирование перекрытия.

После cooldown свежая transport-нотификация может выполнить один
отложенный повтор для этой смены. Должны совпасть текущая ключевая эпоха, допустимый
внутренний адрес и актуальное назначение. Остановленный клиент, закрытое
устройство или запрет roaming не допускают повтор; перед каждой пачкой
снова проверяются ключ и адрес. Уже переданные сети пакеты отозвать нельзя.
После попытки снимок остаётся без разрешения на отправку до следующей
свежей смены либо исходного срока 1100 мс. Смена назначения и отправка
никогда не продлевают этот срок. Прежняя очистка через 100 мс
освобождает и неактивные снимки. Новых таймеров или обработчиков на каждого
клиента нет. Без следующего подходящего пакета до истечения срока попытки
не будет.

Обычное кольцо по-прежнему выбирает пакеты моложе 500 мс. Сохранённый снимок
может пережить это кольцо; новые ответы добавляются только при следующей
проверенной смене адреса. [Отчёт v25](../validation-v25.ru.md) сравнивает
изменения с v24 и описывает оставшиеся ограничения доставки и дедлайнов.

Восстановление может не вернуть старые пакеты, пакеты другой эпохи, при
частых или одновременных сменах адреса, вытеснении кеша и выходе за окно
повторов клиента. Во время смены добавляется трафик. Зарегистрированный
клиент с возможностью послать корректный transport тоже может вызвать
ограниченную повторную отправку; лимиты не доказывают обратную достижимость.
Повторяющийся шифротекст виден в сети. Гарантий против DPI и связывания
потоков у этой опции нет. На действующих серверах оставьте её выключенной,
пока эти компромиссы проверяются в лаборатории.

[Проверка границ](../validation-v23.ru.md) использовала прежний предел
4096 пакетов; [v24](../validation-v24.ru.md) добавил замороженный снимок.
V25 сохраняет и дополняет снимок между попытками. Бюджеты шифротекста
по 2 МиБ прежние, но теперь один клиент может использовать общий допуск
в четыре попытки/с. Для крупных пакетов раньше может закончиться бюджет
байтов. Кеш общий: один клиент может вытеснить недавние ответы другого.
Для TCP-подключения помощника и
TLS-handshake на выходе задан таймаут в секунду; при RTT 1400 мс запуск
в лаборатории не состоялся. Успех обычного TCP с большим таймаутом
не подтверждает работу mTLS на таком RTT.

## Запуск в одноразовом стенде

Процессы намеренно требуют root, имена машин `kit-entry`/`kit-exit`, частные
IPv4 и флаг `--vm-test`. Это не службы для действующих серверов. Нужен
стенд с рабочим DNAT/SNAT, двумя нативными клиентами AWG и
[C-фильтром](../README.ru.md). Сохраните исходные бинарники и определения
служб.

На A нужен `conntrack`; также нужны Python 3, nftables и OpenSSL. Конфиг
каждого процесса и его закрытый ключ разместите в директории, доступной
только root, с правами 0600 на обоих файлах. Поля конфига приведены ниже:
`cert`/`key` принадлежат роли, а `ca` содержит закреплённый сертификат другой
роли.

```json
{
  "entry": "192.168.76.10",
  "exit": "192.168.76.20",
  "vpn_port": 32497,
  "cert": "/root/flow-confirmation/entry.pem",
  "key": "/root/flow-confirmation/entry.key",
  "ca": "/root/flow-confirmation/exit.pem",
  "events": "/run/coldwire-flow/events.sock",
  "status": "/root/flow-confirmation/entry-status.json"
}
```

В стенде были отдельные краткоживущие сертификаты Ed25519 с нужным IP SAN
и назначением для клиентской/серверной аутентификации. B слушает TCP 39101
и принимает только адрес A с его клиентским сертификатом. A сверяет IP B
с закреплённым серверным сертификатом. До применения правил проверьте
отказ в соединении без клиентского сертификата.

Создайте `/run/coldwire-flow` от root с правами 0700. Сначала запустите
процесс B:

```sh
sudo python3 agent.py --vm-test exit /root/flow-confirmation/config.json
```

Отдельный модифицированный бинарник AWG запускается с
`COLDWIRE_LAB_PROOF_SOCKET=/run/coldwire-flow/events.sock`. Сокет должен
существовать до первого проверенного пакета: прототип инициализирует его
один раз. Исходный бинарник AWG сохраните.

На A нужен вариант C-фильтра с классификацией, очередь 100. В родительской
директории выполните `make check-handshake`, затем запустите
`prefilter-handshake` с прежним файлом ключей и аргументами
`--vm-test --queue 100`. Сборки `prefilter`/`prefilter-batch` по-прежнему
предназначены для обычных примеров C-фильтра.

Вариант добавляет локальные метаданные netfilter после проверки:
`0x40000000` означает выполненную классификацию, `0x20000000` обозначает управляющее
сообщение. Остальные биты метки сохраняются, замена полезной нагрузки не
передаётся. В сетевых пакетах этих меток нет. Допуск использует
`0x10000000`; пример очищает все три зарезервированных бита на входе.
Старый бинарник без метки в объединённых правилах закрывает доступ:
при несовпадении бинарника и правил проверяйте этот счётчик отбрасывания.

Проверьте и загрузите
объединённый `lab-rules.nft.example`, заменив прежние экспериментальные
таблицы ограничителя и очереди одной транзакцией nftables. Старый обработчик
очереди не должен оставаться активным. Обычную таблицу NAT релея сохраните.
Перед загрузкой правил заведите таймер отката, затем запустите процесс A:

```sh
sudo python3 agent.py --vm-test entry /root/flow-confirmation/config.json
```

Оба файла состояния показывают соединение и ограниченные по размеру
счётчики. A также записывает допуски, срок действия и заменённые потоки.
Измеряйте ранние потери клиентов, NFQUEUE, полезную скорость, доставку
проб и CPU всей VM вместе. [Последний отчёт](../validation-v25.ru.md)
проверяет восстановление при последовательных сменах адреса.
В [v24](../validation-v24.ru.md) описана исправленная модель NAT стенда.
В [v23](../validation-v23.ru.md) остаётся отдельная граница запуска.
В [v22](../validation-v22.ru.md) остаются исходные контроли восстановления
и исправления измерителя.
Прежние проверки допуска и холодного старта приведены в [v19](../validation-v19.ru.md).

Для отката остановите процесс A, пока его таблица ещё существует. Удалите
объединённую экспериментальную таблицу, затем остановите C-фильтр.
Верните исходную команду службы AWG на B и окружение, перезапустите службу
и переподключите два лабораторных клиента. Остановите процесс B и проверьте
пробы через обычный DNAT. Эти действия не предназначены для выполнения
на действующем сервере в ходе эксперимента.
