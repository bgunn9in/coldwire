# V39: задержки после перезапуска и истечение срока хранения

[English](validation-v39.md) | Русский

Итоговый вариант с ранней пробой доставил все 1 440 000 полезных UDP-пакетов и 400 ответов ping в четырёх прогонах. Из них 37 ответов пришли позже секунды; максимум RTT составил 1736,487 мс. Контроль на прежнем алгоритме в этом же стенде дал 2052,289 мс. Это отдельные прогоны с джиттером, поэтому результат не гарантирует такого же улучшения в других сетях. Обычные установщики по-прежнему не включают прототип.

## Откуда берётся задержка

При аварии помощника A последовательно приходится ждать перезапуска systemd и запуска Python, соединения TCP, взаимной проверки TLS, подтверждения nonce узлом B, отправки пробы из очереди и возврата достоверного подтверждения потока. Затем нужны установка правил, выпуск пакетов и прохождение сети. Контроль `tap25b` с проверенным начальным допуском воспроизвёл ping 2231,314 мс без потерь в очередях, коммутаторе и захватах. Худший запрос провёл в C 1862,354 мс.

С итоговым сроком хранения 2,6 с контроль `normalbase26` дал максимум 2052,289 мс. Из них 1680,154 мс заняло удержание. A поставил nonce для порта 42501 в отправку через 1109,12 мс после SIGKILL и принял подтверждение через 1797,18 мс. В `earlyup1200a` эти времена составили 1023,04 и 1484,04 мс. Интервал от постановки запроса до подтверждения сократился с 688,06 до 461,00 мс. Джиттер пути и время TLS в этих прогонах тоже различались. Удержание худшего ping во втором прогоне заняло 1348,270 мс.

Полный внешний трафик теперь захватывается пассивно на коммутаторе Windows в течение восьми секунд. В гостевой A остаётся только редкий служебный TCP. Сопоставление достоверного внешнего шифротекста с внутренними номерами пакетов и записями nonce в C позволяет отличить истечение срока хранения от отклонения повторов. Диагностические сессионные ключи остаются в закрытой root-папке одноразовой VM выходного узла и не попадают в репозиторий. Время удержания измеряется монотонными часами A, внешние интервалы пути часами одного хоста, а RTT часами захвата клиента.

## Прежняя потеря 122 UDP-пакетов

Сохранённый захват источника v38 `queueup1200` содержит 122 пропавших пакета среди номеров 154526 по 154656. Они отправлены через 120,404 до 142,259 мс после начала первой смены NAT и относятся к первому изменённому отображению, порту 42501. Подтверждение этого порта пришло на A через 2467,189 мс после SIGKILL. Для фактического выпуска ещё требовались установка правил и доставка снимка допуска в C.

В новом контроле намеренно увеличена только пауза перезапуска A с 200 до 1200 мс и использован прежний срок хранения 2,5 с. В `edgebase25` потеряны 92 полезных UDP-пакета и один ping. Для каждого из этих 92 пакетов есть достоверное совпадение на входе, запись удержания и запись истечения срока в C. Копии отправки на B и записи отклонения replay-фильтром отсутствуют. Подтверждения старых потоков приходят примерно через 2584 мс, установка правил заканчивается через 2614 мс. Счётчики потерь NFQUEUE, коммутатора и захватов равны нулю. Так непосредственно воспроизведено истечение срока при передаче подтверждения между компонентами.

Для прежних 122 пакетов нет индивидуальных записей C и полного внешнего захвата. Точное место их потери остаётся недоказанным. Их времена согласуются с истечением срока хранения; новый пример с 92 пакетами не устанавливает задним числом судьбу старых пакетов. Итоговый срок хранения остаётся 2,6 с.

## Сохранённое изменение

A отмечает ожидающие запросы nonce, которые полностью вышли из его буфера TLS. На последующем проходе обслуживания он может запросить одну раннюю пробу через root-запрос `CWT1`. C ограничивает такие пробы до 32/с с запасом 32 внутри прежнего общего бюджета 64/с с запасом 64. После подтверждения приёма nonce узлом B A может запросить одну резервную пробу `CWS1`. Поздние неотправленные запросы не задерживают пробу для уже отправленного запроса.

Проба не выдаёт допуска. B по-прежнему должен проверить достоверное транспортное событие после приёма запроса nonce; проверка повторов и источника сохраняется. A заново сверяет точное текущее поколение conntrack. Тесты отклоняют события до запроса, заблокированную или частичную запись TLS, просроченные nonce и неверные локальные запросы. Самопроверка C подтверждает, что смесь ранних и обычных проб не превышает общий бюджет.

Вариант с немедленной пробой после записи отклонён. При джиттере UDP может опередить запрос TLS, после чего нужна резервная проба. С искусственной паузой перезапуска 1200 мс `edgeearly25` потерял 878 UDP-пакетов: у 706 есть записи истечения срока C; у 172 нет записи C, и их число совпало со 172 потерями очереди ядра. Этот прогон не доказывает улучшения относительно контроля. Сохранённый вариант использует прежний цикл обслуживания. Эксперимент v34 остаётся отклонённым; v39 отдельно отслеживает отправленные запросы и проверяет отдельную квоту ранних проб в сценарии аварийного перезапуска.

## Итоговые прогоны

Все прогоны используют четыре локальные VM Debian 13: по одному vCPU и 1024 МиБ RAM, без квоты CPU. Шестнадцать IP шума отправляют 25 000 пакетов/с в течение 70 с, полезный UDP 6000/с в течение 60 с. Между A и B, включая служебный TCP, задана задержка 150±30 мс в каждом направлении. Клиент связан с A локально. Между тремя сменами IP и NAT-порта запрошены паузы 250 мс; SIGKILL на первом пакете с изменённым адресом вызывает перезапуск systemd. Перед нагрузкой проверяется текущее поколение исходного потока и остаток его подтверждённого допуска больше шести секунд.

| Прогон | Направление / байт UDP | Потери UDP / ping | Ping позже 1 с | Макс. RTT, мс |
|---|---|---:|---:|---:|
| normalbase26 | up / 1200 | 0 / 0 | 12 | 2052.289 |
| earlyup128 | up / 128 | 0 / 0 | 11 | 1455.104 |
| earlyup1200a | up / 1200 | 0 / 0 | 8 | 1728.908 |
| earlyup1200b | up / 1200 | 0 / 0 | 11 | 1736.487 |
| earlydown1200b | down / 1200 | 0 / 0 | 7 | 1224.153 |

В каждом итоговом прогоне точно совпадают счётчики отправленного шума и его прихода. Потерь коммутатора и захватов, переполнений и потерь доставки NFQUEUE, а также превышений ёмкости C нет. Потоки шума не получают достоверного допуска. Измеренные пики CPU VM достигают 92,31%; минимальная MemAvailable составляет 465,6 МиБ. Это наблюдения стенда, а не гарантия его пропускной способности. Файлы, ключи и бинарники клиентов не менялись. Использованы те же два нативных клиента Linux, что в v38: Header Protection, S1-S4=12, H1-H4=1/2/3/4, Jc=0, случайные трейлеры, MTU 1280. GUI-клиенты и другие параметры сетевых пакетов в этой серии не измерялись.

## Предел очереди ядра и исключённые измерения

Неудачный контроль немедленной пробы выявил отдельную границу ядра. Ядро 6.12.117 пишет `hash insert failed: -7`. NFQUEUE использует не более 32768 корзин хеш-таблицы, а rhashtable ограничивает число записей удвоенным числом корзин. Поэтому одна очередь удерживает не более 65536 записей даже при запрошенном maxlen 131072. Этот предел отличается от ёмкости C и всё ещё может приводить к потерям при большем накоплении пакетов. См. [реализацию NFQUEUE](https://github.com/gregkh/linux/blob/v6.12.117/net/netfilter/nfnetlink_queue.c) и [инициализацию rhashtable](https://github.com/gregkh/linux/blob/v6.12.117/lib/rhashtable.c). Индивидуальной трассировки 172 сбросов ядра нет; вывод опирается на совпадение числа и времени потерь.

Полный внешний захват внутри A исказил `trace26a`, который не прошёл проверку измерения. В `tap26a` были потери коммутатора и NFQUEUE, а начальный допуск ещё не проверялся. `tap25a` завершился ошибкой настройки до нагрузки. В первом итоговом измерении обратного направления, `earlydown1200`, коммутатор потерял 7099 копий кадров, недоставлены 5489 полезных UDP-пакетов. Он исключён из сравнения фильтра. Повтор прошёл проверку. Эта периодическая пауза приёма гостевой VM остаётся ограничением стенда. Неудачные и исключённые случаи сохранены в JSON.

## Проверки и очистка

Все 52 теста Python проходят на Windows и Linux. Итоговый C проходит самопроверку оптимизированной сборки и ASAN/UBSAN. Тесты охватывают порядок записи, сброс сессии, поздний неотправленный запрос, достоверность события после запроса и общий бюджет проб. Коммутатор проходит внутренние проверки и тесты сокетов localhost. Оба неизменённых клиентских профиля также проходят проверки с итоговым публичным агентом и C без диагностических вставок. Полный набор остальных тестов репозитория повторно не запускался.

[results-v39.json](results-v39.json) содержит прогоны, хеши и результаты очистки. [Сохранённый патч](research/v39-retained.patch) восстанавливает код и тесты от `65fbd03e43d09985613d480540b4c692c2ee3675`; применение и побайтовая реконструкция проверены. Захваты, диагностика, лабораторные ключи и диски остаются локально в игнорируемой папке. Текст документации проверен с Humanizer.

Записи очистки и состояния Git относятся к завершению локального исследования до публикации.

Обычный DNAT и исходный B восстановлены; оба исходных профиля прошли проверки. Экспериментальные хуки, очереди и маршрутизируемый bridge удалены. После смены MAC узла A удалены его устаревшие ARP-записи на соседних VM. Все четыре VM и собственные процессы коммутатора и HTTP-сервера начальных настроек остановлены, локальные порты стенда свободны, SHA512 базового образа совпадает. Прежние отчёты и персональные JSON маршрутизации не изменились. Действующие серверы, VPN пользователя, сетевые настройки хоста, коммиты Git и GitHub не менялись.

Более долгий простой, конкуренция за места при общем NAT, подделка разрешённых адресов и перегрузка канала всё ещё могут приводить к потерям. Для большего накопления пакетов предел 65536 записей потребует отдельного изменения распределения очередей. Эксперимент не даёт гарантии смены адреса за секунду, поддержки IPv6, проверки GUI-клиентов, DPI или длительной непрерывной нагрузки. Строгая фильтрация по-прежнему удаляет маскировочные I/J-пакеты между A и B.
