# Результаты проверки фильтра в VM

[English](validation.md) | Русский

Дата проверки: **10 ноября 2026**. Прототип отбрасывал проверенный
некорректный трафик и сохранял работу обычных клиентов AWG. Без мусора
скорость TCP была близка к DNAT на этом стенде, но расход CPU входного узла
вырос. При потоке 60 000 пакетов/с очередь теряла пакеты, а полезная скорость
стала ниже DNAT. Проверка с перехваченным заголовком также подтвердила,
что фильтр не выполняет авторизацию клиента по ключу.

## Стенд и метод

Четыре локальные VM Debian 13.7 amd64 имели по **1 vCPU и 1024 МиБ RAM**:
клиент C, вход A, выход B и независимый отправитель мусора D. На C работали
два выданных профиля AWG 3.1 в отдельных сетевых пространствах. Использовано
закреплённое в проекте нативное ядро AWG. MTU туннеля — 1280; фильтр не
потребовал новых настроек клиента. Программы серверов и настройки VPN
пользователя вне стенда не менялись.

На входе использовались ядро 6.12.115+deb13.1-cloud-amd64, OpenSSL 3.5.7,
libnetfilter_queue 1.0.5, nftables 1.1.3 и GCC 14.2. QEMU 11.1.3 работал
через WHPX в Windows с CPU `max` и прежним локальным исправлением перезагрузки.
WSL2, изменения адаптеров и маршрутов Windows не использовались. Гостей
соединял обучающийся Ethernet-коммутатор через localhost; во всех итоговых
прогонах он не терял кадры из-за переполнения очереди. Прототип использовал
один процесс, без Go SDK и Docker. GCC устанавливался только для одноразовой
сборки и проверки.

iperf3 передавал TCP между сетевым пространством клиента и туннельным
адресом B. Для каждого режима и направления выполнены три прогона по
12 секунд измерения после двух секунд прогрева. Порядок: DNAT/фильтр,
фильтр/DNAT, DNAT/фильтр. CPU всего гостя A вычислялся через `/proc/stat`.
RSS получен из `/proc` процесса фильтра. Хеши исходника и бинарника,
отдельные измерения находятся в [results.json](results.json).

## TCP без мусора

Указаны медианы трёх прогонов. Отправка означает C→B, загрузка — B→C.

| Направление | DNAT, Мбит/с | Фильтр, Мбит/с | CPU входа с DNAT | CPU входа с фильтром |
|---|---:|---:|---:|---:|
| Отправка | 234.61 | 233.45 | 3.25% | 33.10% |
| Загрузка | 226.13 | 224.83 | 3.53% | 21.75% |

RSS фильтра составлял **6.30–6.31 МиБ**, без памяти очереди и сокета в ядре.
Сокет показывал приёмный лимит 8 МиБ; очередь ограничена 2048 пакетами.
Эти лимиты не означают постоянного занятия всей памяти. На тестовую службу
также действовал лимит cgroup 64 МиБ; бинарник сам не устанавливает службу
и не задаёт ей это ограничение.

Близкая скорость не определяет предел фильтра. На стенд также влияют QEMU,
WHPX, программный коммутатор, клиент и выходной узел.

## Мусор одновременно с TCP

D повторял 256-байтную нагрузку, случайно выбранную для каждого прогона.
Заданные скорости 10/30/60 тысяч пакетов/с достигнуты с отклонением менее
1 пакета/с. Каждая строка — один короткий прогон, а не повторное измерение
предельной нагрузки. iperf3 измерял восемь секунд после одной секунды
прогрева внутри 12-секундного потока мусора.

| Мусор, пакетов/с | DNAT, Мбит/с | Фильтр, Мбит/с | CPU входа с DNAT | CPU входа с фильтром |
|---:|---:|---:|---:|---:|
| 0 | 232.76 | 209.18 | 2.04% | 29.68% |
| 10 000 | 182.54 | 178.93 | 2.40% | 33.47% |
| 30 000 | 134.75 | 153.69 | 10.21% | 46.74% |
| 60 000 | 162.68 | 125.42 | 59.70% | 66.67% |

При 60 тысячах зарегистрирована **3281 потеря в очереди**, при нуле потерь
приёма netlink в момент снимка. Счётчики включают мусор и полезный трафик;
по ним нельзя определить, какие именно пакеты потеряны. Проверки клиента
проходили после каждой нагрузки. Результаты немонотонны; переносить их
на канал хостера или реальную DDoS-атаку нельзя.

## Отбрасывание и таблица соединений

Каждая выбранная нагрузка отправлялась 9000 раз при 3000 пакетах/с.
Поступление измерялось отдельными счётчиками на B. UDP GRO объединяет
датаграммы, поэтому их число получено из объёма полезной нагрузки после
вычитания 28 байт на каждый учтённый IPv4/UDP skb. В контрольном DNAT
все пять вариантов дали ровно 9000 датаграмм на B.

| Входные данные | Дошло до B с DNAT | Дошло до B с фильтром |
|---|---:|---:|
| Случайная нагрузка | 9000 | 0 |
| Неверный HeaderProtectionKey | 9000 | 0 |
| Распознанный заголовок, неверный MAC1 | 9000 | 0 |
| Правильный MAC1, некорректное начало Noise | 9000 | 9000 |
| Распознанный заголовок данных, неверное содержимое | 9000 | 9000 |

При 40 000 пакетах с 4096 исходными UDP-кортежами общий счётчик conntrack
на A изменился **34→35 с фильтром** и **37→4114 с DNAT**. На этот счётчик
также влияют SSH и истечение срока других записей. Раннее отбрасывание
предотвратило накопление, наблюдаемое в контрольном варианте.

## Проверенная совместимость и ограничения

- Оба выданных нативных клиента выполнили новые рукопожатия, HTTPS, DNS
  и DF ping с нагрузкой 1200 байт. Рукопожатие по инициативе B проверило
  MAC1 входящего ответа.
- Смена исходного IP и порта клиента работала. Проверено совпадение
  внешнего порта клиента с входным портом A.
- Неверный HPK и незарегистрированная клиентская идентичность не давали
  доступа к VPN.
- Сто пакетов с поддельным адресом и портом B в исходном направлении
  проверены и отброшены. Опубликованные пример nft и CLI экспорта
  также использовались успешно.
- Принудительная остановка процесса очереди прекращала фильтруемый трафик.
  Удаление только экспериментальной таблицы возвращало DNAT; правила
  реле без значений счётчиков совпадали с исходными.
- У D не было файла ключей. Он отправил 100 пакетов из перехваченного
  настоящего префикса/заголовка данных с изменённой нагрузкой. Фильтр их
  пропустил; обычный клиент продолжал работать. Поступление пакета не
  доказывает владение клиентским ключом и даже HeaderProtectionKey.

Все **14 автономных тестов** прошли в оптимизированной сборке и с
ASan/UBSan: повреждённые данные, независимые криптографические векторы
и намеренно допускаемые повтор/подмена нагрузки. Прошёл `make -B check`.
Прежние **48/48 модульных тестов** проекта на Windows также прошли
без пропусков.

## Воспроизведение и исправления

Сборка и экспорт ключей описаны в [руководстве](README.ru.md).
Используйте изолированные A/B/C/D с частными адресами и выданные нативные
профили. SSH должен идти отдельно от туннеля. На B привяжите iperf3
к туннельному адресу:

```bash
iperf3 -s -B 10.8.1.1
```

На C с активным профилем в `pf-client1` повторяйте команды для каждого
режима. `-R` задаёт загрузку. На A переключайте только таблицу эксперимента.

```bash
ip netns exec pf-client1 iperf3 -c 10.8.1.1 -t 12 -O 2 -J
ip netns exec pf-client1 iperf3 -c 10.8.1.1 -t 12 -O 2 -J -R
```

Снимайте `/proc/stat` на A, RSS фильтра и
`/proc/net/netfilter/nfnetlink_queue` до и после каждого прогона.
Для нагрузки используйте отдельный D; измеряйте достигнутую скорость
отправки, потери коммутатора и восстановление клиента. Лабораторный мусор
не должен отправляться на публичные адреса.

Первый закрытый коммутатор рассылал каждый кадр всем и завершился
при заполнении буфера на заданных 100 тысячах пакетов/с. Его заменил
обучающийся коммутатор с ограниченными очередями и отбрасыванием кадров
вместо завершения. Итоговые измерения повторены на нём. Первоначальный
запрос размера сокета также ограничивался обычным лимитом приёма ядра.
Итоговая сборка явно использует SO_RCVBUFFORCE и выводит полученный размер;
криптографические тесты и сетевые замеры повторены. Подготовка повторного
прогона исправлена для замены уже существующего IP стенда. Обычные
установщики из-за этих изменений не менялись.

Все гости и вспомогательные процессы остановлены, порты localhost освобождены.
Физические приложения Windows/macOS/Android/iOS, другие дистрибутивы для
прототипа, совместная работа с REALITY, длительная нагрузка и устойчивость
к DPI не проверялись. Фильтр отбрасывает I1/Jc на участке A→B и допускает
повторно использованные либо созданные распознаваемые пакеты. В обычную
установку он не включён.
